# Review: event wiring & UI — pi-autoresearch (2026-11-16)

Scope: `extensions/pi-autoresearch/index.ts` hooks (session_start/tree/before_switch/shutdown, agent_start/end, before_agent_start, tool_call, tool_execution_end, session_before/compact), pending-resume/drift mechanics, subagent-wait-guard, compaction.ts, hooks.ts, commands.ts, shortcuts.ts, bash-shell.ts, paths.ts, subagent-probe.ts, widget/overlay code.

Total findings: **17** (5 high, 8 medium, 4 low).

## 1. Dead code & stale branches

### F1. `autoresearchHelp` is dead code — HIGH (low risk, easy win)
- `index.ts:3192-3227` defines a 35-line `autoresearchHelp()` closure. Grep shows **zero call sites** — the real help is `renderAutoresearchHelp()` from `commands.ts` (imported line 192, used at 11463).
- Worse: the dead text still advertises parallel modes as working fan-out features (`parallel-best-of-n <N> <goal> — try N hypotheses at once`), while `AUTORESEARCH_SUBCOMMANDS` (parallel/config-ui.ts:56-58) marks them "parallel tools removed (scope split)". Any future reader gets two contradictory descriptions of the same command.
- **Fix:** delete `autoresearchHelp` entirely.

### F2. Dead null-check AFTER dereference in `expeditionDriftBranchText` — HIGH (latent crash)
- `index.ts:2826-2827`:
  ```ts
  const body = nudge.replySuffix.replace(/^Next: /, "");
  return nudge === null ? null : `Continue the expedition now: ${body} ...`;
  ```
  The `nudge === null` guard is evaluated **after** `nudge.replySuffix` is dereferenced. If `expeditionCloseNudge` returns null (it can: `index.ts:11278-11287` returns null for non-expedition chain, null campaignId, unresolvable dir, wrong phase — three of which are reachable between the pre-check at 2815-2824 and the call, since both do their own fs reads), this throws a TypeError inside a drift-resume composer.
- **Fix:** check null first: `if (nudge === null) return null; const body = ...`.
- Bonus: the pre-check (2816-2824) and `expeditionCloseNudge` (11278-11287) duplicate the same guard chain (chain?.expedition, campaignId, resolveCampaignDir, readState, phase check) — extract a shared `resolveExpeditionCampaignState(ctx, chain)` helper.

### F3. Dead sync helper duplication `hasAutoresearchRules` — LOW
- `index.ts:3055-3058` defines `hasAutoresearchRules` (checks `.auto/prompt.md` existence); grep shows no call sites in the file. Leftover from the pre-compaction design where prompt.md was injected every turn.
- **Fix:** verify with a full-repo grep and delete.

## 2. Composer duplication (the biggest maintainability cost)

### F4. Five composers re-implement the same campaign-branching decision — HIGH
- The "which mode am I in, which wording do I send" branching is copy-pasted across:
  - `composeResearchDriftMessage` (2808-2825): expedition branch → completion-snapshot branch → RESEARCH_RESUME_TEXT.
  - `composeCampaignResumeMessage` (2850-2870): research scan (duplicated state-root check!) → expedition branch → completion snapshot → candidate text.
  - `composeDriftResumeMessage` (2872-2905): research → candidate → no-ledger → legacy.
  - `composeCompactionResumeMessage` (3022-3044): research → candidate → legacy.
  - send-time replacement in `sendPendingResumeIfReady` (2521-2529): a *fourth* re-derivation with regex sniffing (`/run_experiment|log_experiment/.test(message)`, `/candidate_branch/.test(message)`).
- Every new campaign type (research → candidate → expedition → charter chain) added one more hand-rolled branch to each composer. The snapshot condition `readable && allClosed && !stopTriggered && phase === "research"` is spelled out 3 times (2818, 2861, plus its own copy in `notifyAutoResumeLimitReachedAsync` 2565). The candidate "STOP on manual_check_required" stanza appears in 4 variants.
- **Fix:** one table-driven resolver `resolveLoopMode(workDir, runtime): { mode: "legacy"|"research"|"expedition"|"candidate", snapshot? }` + `composeResume(mode, kind: "drift"|"plain"|"compaction")`. The send-time regex sniffing disappears because messages would carry a mode tag (store `{mode, text}` in `pendingResumeMessage` instead of raw string).

### F5. Triplicated "paused" notify text — MED
- `index.ts:2929-2934` (deliverDeferredDriftNudge) and `index.ts:3684-3690` (agent_end drift-limit branch) are byte-identical ternary chains; `sendPendingResumeIfReady` re-uses a fourth wording. One drift-policy change must be applied in 2-3 places.
- **Fix:** single `composePausedNotice(workDir, ctx)`.

## 3. Timers & races

### F6. Magic-number timer lattice with undocumented coupling — MED
- `SETTLED_WINDOW_MS = 800` (2390), `SUBAGENT_DEFER_RECHECK_MS = 30_000`, `SUBAGENT_DEFER_FUSE_MS = 600_000` (subagent-probe.ts:17-21), ping unsubscribe `setTimeout(..., 1000)` (index.ts:2361), spinner `setInterval(..., 80)` (7112). The 800ms window exists to outlast pi's internal retries (comment 2388-2390) — that pi-internals coupling is documented, but nothing encodes the *relationship* "800 > retry(0)+retry(100)" in code; a pi timing change silently breaks resume delivery. Tests already hardcode `setTimeout(r, 1100)` (research-branch-wiring.test.mjs:165) — the assumption is duplicated again.
- **Fix:** export `SETTLED_WINDOW_MS` and derive the test wait from it; add a named constant with the derivation comment next to the number.

### F7. Module-scoped mutable singletons: `subagentCtx`, `subagentGuardArmed`, `subagentRecheck` — MED
- `index.ts:2327-2350`: guard state lives in module-level `let`s shared across ALL sessions of the process. `subagentCtx` is overwritten by every `session_start`/`agent_start` (3553, 3585); a completed subagent event re-probes only the **latest** session's deferral (`subagentRecheck` 3014-3020). With two concurrent sessions (pi multi-session / `/tree`), session A's deferral is invisible while session B holds `subagentCtx` — the fuse (10 min) eventually rescues it, but the nudge arrives late or never within the session that matters. `runtimeStore` is properly keyed by session; the guard state is not.
- **Fix:** move `subagentGuardArmed`/probe-in-flight into the per-session runtime (or a keyed map); route `subagents:rpc` events through a registry of active contexts instead of a single `subagentCtx`.

### F8. `sendSubagentPing` leaves up to N orphan subscriptions per session_start — LOW
- `index.ts:2352-2363`: each call subscribes a reply listener and unsubscribes it via a 1s timer. On every `session_start` (and it fires even when pi-subagents is absent forever), one closure + one timer live for 1s. Harmless today, but there is no cancellation on `session_shutdown` — a shutdown within the 1s window fires into a dead bus. Fail-open by design, so: low.
- **Fix:** track the ping timeout in `unsubscribeSubagentEvents` cleanup.

### F9. `reprobeSubagentDeferral` re-checks `runtime.subagentDeferral` after an await, but not `ctx` liveness — MED
- `index.ts:2952-2987`: after `await probeSubagentActivity(...)`, the code checks `if (!runtime.subagentDeferral) return;` (reset guard) — good — but never re-validates that `ctx` is still the live session (it was captured at deferral time). If the session was switched/shutdown mid-probe, `schedulePendingResume` re-arms a timer on a removed runtime and `pi.sendUserMessage` at delivery targets a stale session. `session_shutdown` cancels deferral (3571), which closes most of the window, but a `session_before_switch` does **not** cancel it (3563-3565 only clears overlay) — the deferred nudge can fire into a session the user just navigated away from.
- **Fix:** cancel subagent deferral in `session_before_switch` too (symmetry with `cancelSubagentDeferral(getRuntime(ctx))` in session_tree), or verify `getRuntime(ctx) === runtime` after the await.

## 4. Business-logic asymmetries (fail-open vs fail-closed)

### F10. `agent_end` drift-limit check races the send-time gates — MED (design inconsistency, not a bug today)
- Ordering of gates differs between the three resume paths:
  - `agent_end` (3644-3702): stopReason → manualCheck → subagent-defer → drift++ → schedule.
  - `deliverDeferredDriftNudge` (2925-2947): mode/experiments checks → **drift-limit → manualCheck** → stopReason → drift++.
  - `sendPendingResumeIfReady` (2493-2529): mode → halted/pending → stale-wording → settled → stopReason. **No manual-check re-check here** — a pending-op appearing inside the 800ms window is caught only by `campaignPendingOpSync`/`halted` (which do cover the research pending case, so the candidate pending-op path relies on `campaignPendingOpSync` — OK), but the *candidate* pending-op appearing after scheduling is covered while a *research* pending-op is covered only via `researchNow.halted`. The asymmetry is subtle and only holds because both scans happen to be sync. Any new async gate added at send time must remember to re-check; nothing enforces it.
- **Fix:** extract a single `evaluateResumeGates(ctx, runtime): "deliver"|"cancel"|"reschedule"` used by all three paths, with one documented gate order.

### F11. `sendPendingResumeIfReady` leaves the message parked forever when the agent is unsettled — MED (by design but undocumented risk)
- `index.ts:2511-2512`: `if (!isAgentSettled(ctx)) return;` — returns WITHOUT cancelling and WITHOUT re-arming. If the timer fired while the agent was busy, `pendingResumeMessage` stays set with `pendingResumeTimer = null`; delivery then happens only if some later `ensurePendingResume` calls `reschedulePendingResume` (2552-2555). A drift-path message (already counted `consecutiveDriftResumes++` + `markAutoResumeSent` at schedule time, 3677-3678) that never fires means the counter was consumed with no nudge delivered — the user sees silence, and the drift budget is spent.
- **Fix:** on the unsettled branch, re-arm the timer (retry until settled) instead of returning bare; or move the counter increment to actual delivery (it was moved *out* of agent_end into delivery for the deferral path — do the same here; see F12).

### F12. Drift counters increment at SCHEDULE time on the ordinary path but at DELIVERY time on the deferral path — HIGH (semantic split-brain)
- Ordinary path: `agent_end` increments `consecutiveDriftResumes` and calls `markAutoResumeSent()` *before* `schedulePendingResume` (3677-3678) — the resume may still be cancelled at send time (mode off, halted, stale wording) and the counters are already spent.
- Deferral path: `deliverDeferredDriftNudge` (2944-2946) increments *at delivery*, explicitly documented as "design Decision 3" (2937-2941).
- Two different ownership rules for the same counters in two adjacent code paths. Concrete consequence: turn drifts → scheduled → `/autoresearch off` before the 800ms window elapses → send-time cancel (2496-2498) → but `autoResumeTurns` already ticked toward the 200 limit (`AUTORESUME_TURN_LIMIT`, line 295) for a message that was never sent.
- **Fix:** standardize on delivery-time accounting for both paths (aligns with the documented Decision 3).

### F13. `deliverDeferredDriftNudge` duplicates the drift-limit notify with a stale campaign check — MED
- `index.ts:2929-2934` uses `researchScanSync(...).blocks` / `campaignActiveSync(...)` to pick the notify text, but does NOT consult `getRuntime(ctx).researchStateRoot` (unlike `agent_end`'s copy at 3684 which also omits it — actually both omit it). A state-root campaign user hitting the drift limit sees the generic "run /autoresearch <goal>" notice prescribing a blocked flow. Inconsistent with `composeCampaignResumeMessage` which is state-root aware (2853-2856).
- **Fix:** shared composer (see F5) that includes the stateRoot check.

### F14. `ensurePendingResume` empty-string claim relies on send-time falsy check — LOW (fragile contract)
- `index.ts:3617-3625` sets `pendingResumeMessage = ""` as a mutex claim; `sendPendingResumeIfReady` treats falsy as "nothing to send" (2494 `if (!message) return;`). The invariant lives in a comment; a future refactor replacing `!message` with `message === null` silently double-schedules. Type the claim: `pendingResumeMessage: { text: string } | null` with an explicit `{claimed:true}` state, or use a dedicated boolean.
- **Fix:** make the claim a distinct typed state rather than an overloaded empty string.

## 5. Extraction from index.ts (supportability)

### F15. The resume/drift subsystem (~lines 2380-2560 + 2780-3060, ≈ 460 lines) should be a module — HIGH
- Self-contained: needs only runtime, workDir resolvers, the campaign scan predicates, and `pi.sendUserMessage`. Its 5 composers, 3 gate paths, timer lattice and counter policy are the most-iterated, most-reviewed code in the file (comments cite review M-4, design §5, Decision 3, review B2, bd drift-nudge fix, review R1A/B4 — six separate review passes). Extracting `resume-policy.ts` (composers + gates + schedule machinery) behind an explicit context object would (a) make the gate order unit-testable without the fake-pi harness, (b) cut index.ts by ~5%.
- **Fix:** `resume-policy.ts` with `createResumePolicy(deps)`; index.ts keeps only hook registration.

### F16. Subagent-wait-guard (~2320-2363 + 2913-3021, ≈ 150 lines) should join subagent-probe.ts — MED
- The probe (event-RPC client) already lives in its own file; the *policy* (defer/reprobe/fuse/ping) lives in index.ts with module-scoped state (F7). One file `subagent-guard.ts` owning probe+policy+state, wired via a context getter, removes the module singletons and the split-file incoherence.
- **Fix:** merge into `subagent-guard.ts`; export `createSubagentGuard(runtimeAccessor, events)`.

### F17. Widget/overlay/UI plumbing (~3090-3545 + 7100-7230, ≈ 600 lines) — MED
- `updateWidget` (3219+, three rendering strategies: expedition / starter / dashboard / tree), overlay dashboard `ui.custom` block with scroll handling, spinner, `syncBriefPreview`/`briefTranscriptText` (9616-9635), `clearSessionUi`/`clearOverlay` — all pure TUI concerns interleaved with campaign logic. `briefTranscriptText` also returns user-facing strings in Russian while the rest of the extension's model-facing text is English (consistent for the human owner, but worth a note: two languages in one file's string literals).
- **Fix:** `widget.ts` + `overlay.ts` receiving a snapshot object; index.ts passes `(state, runtime, workDir)` and keeps zero rendering code.
