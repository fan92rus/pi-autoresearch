# Review: Ordinary-loop core (index.ts + jsonl/lens/confidence/observer/measurement)

Scope: `reconstructState` (~3110-3340), `init_experiment` (~3951-4200), `propose_hypothesis` (~4230-4470), `run_experiment` (~4836-5580), `log_experiment` (~5614-6230), run-links wiring, keep/discard/auto-revert, measurement.ts epochs, jsonl.ts, lens*.ts, confidence.ts, observer.ts. Read-only review; every claim below was verified against the actual code.

## 1. Dead / legacy code

### 1.1 [MED] Legacy `autoresearch.sh` still accepted by the benchmark guard
`index.ts:810-821` (`isAutoresearchShCommand`): the comment says legacy `autoresearch.sh` is "still accepted for in-flight sessions", yet `autoresearchScriptPath`/`sessionFilePath` now point only at `.auto/measure.sh`. The regex keeps matching a script name the rest of the pipeline no longer produces. Suggestion: either drop `autoresearch\.sh` from the regex (breaking only pre-measure.sh sessions, which no longer exist per paths.ts), or date the deprecation and add a removal issue. Risk: two accepted spellings of "the benchmark" drift apart on future edits.

### 1.2 [LOW] `readConfig` silently swallows a corrupt config
`index.ts:1034-1042`: `catch { return {} }` — a corrupt `.auto/config.json` degrades to defaults (`workingDir` redirect lost, `maxIterations` lost, `experiment_max_minutes` lost) with zero warning. Contrast with `lens-config.ts:104` which returns `{status:"unparseable", error}` and surfaces it in init. Suggestion: at minimum log a `pi.debug`/notify once; better: return a discriminated result like `readCampaignConfig` does, so `resolveWorkDir` can warn "config unreadable, using ctx.cwd". Fail-open here is deliberate for resilience, but silent fail-open is a support trap (user's `workingDir` mysteriously ignored after a hand-edit breaks JSON).

### 1.3 [LOW] `explore` status kept alive as reader-only zombie
`index.ts:6428, 6468-6469`: legacy ledger rows with status `"explore"` are excluded from counters "for backward compatibility; the status is no longer writable". This is fine, but the exclusion logic is spread over two places (index drift counters + observer). If any ledger older than that change still exists, keep it; otherwise this can be folded into `jsonl.statusFrom` (map `explore`→`keep` at reconstruct time) and deleted everywhere else. Verify with the oldest test fixtures first.

## 2. Duplication between index.ts and modules

### 2.1 [HIGH] `inferMetricUnit` implemented twice, already diverged in scope
`jsonl.ts:63-70` (`inferMetricUnit`) vs `index.ts:5816-5824` (inline unit inference in `log_experiment`'s secondary-metric registration). Same rules (µs/_ms/_s/_sec/_kb/_mb) copied verbatim in two files. A future unit (e.g. `_gb`, `ms` suffix without underscore) will be added to one and not the other, silently splitting the reconstructed state from the live state. Suggestion: export `inferMetricUnit` from jsonl.ts and import it in index.ts. One-line fix, removes a whole class of drift.

### 2.2 [HIGH] The git auto-revert script is duplicated verbatim in `log_experiment`
`index.ts:6145-6152` (status≠keep && ≠budget_exceeded) and `index.ts:6160-6167` (budget_exceeded) contain the identical multi-line `git checkout -- . ':(exclude,...)'` + `git clean -fd -e ...` script. Any fix to the exclude patterns (e.g. a new autoresearch artifact dir) must be applied twice; a miss means budget_exceeded runs stop preserving files. Suggestion: extract `const REVERT_SCRIPT = ...` (or a `revertWorkingTree(workDir)` async helper) used by both branches; the budget branch keeps only its extra steer message.

### 2.3 [MED] `findBestRunNumber` (index.ts:1368-1390) re-implements best-scan already in `findBestMetric`
Both walk epoch results filtering `keep`/`metric>0` with direction-aware min/max; `findBestRunNumber` additionally tracks the index. `findBestMetric` (index.ts:~1425-1432) uses `Math.min(...kept)` spread (which also has a latent stack risk on very large segments — `Math.min(...arr)` with >100k entries throws). Suggestion: one `findBestRun(results, segment, direction, epoch): {metric, runNumber} | null` used by both; kills the duplication and the spread risk.

### 2.4 [MED] Segment/epoch helpers (`currentResults`/`resultEpoch`/`segmentEpoch`/`epochResults`/`findBaselineMetric`/`computeConfidence`) live in index.ts but are pure ledger semantics
`index.ts:841-920` — these operate on `ReconstructedRun`-shaped data and are needed by report.ts/observer.ts/council.ts through other paths (council re-parses the ledger with its own code at council.ts:597; exhaustion-hints.ts:539 openly "mirrors reconstructJsonlState"). The epoch/segment semantics are the project's most safety-critical invariant (cross-epoch comparison ban) and are currently spread across index.ts + exhaustion-hints mirror + measurement.ts epoch counter. Suggestion: move `currentResults/resultEpoch/segmentEpoch/epochResults/findBaselineMetric/findBestMetric/computeConfidence/findBaselineSecondary/priorEpochBest` into jsonl.ts (or a new `ledger-metrics.ts`), exported, and make exhaustion-hints' `scanLogContexts` reuse the shared segment-splitting rule instead of mirroring it. This is the single highest-leverage cohesion fix in the ordinary loop.

### 2.5 [MED] 12 scattered `loadTree(workDir)` calls with no shared error path
`index.ts:1134,1580,1700,3247,3464,4319,4964,5020,5118,5744,5759,7754`. Every call site re-checks `treeExists` then null-checks then acts; several wrap in try/catch "best-effort" with different swallow depths. Within one `run_experiment` execute, the tree is loaded up to 3 times (validation at 4964, baseline check at 5020, run-links node resolution at 5118) — each load is a full readFileSync+JSON.parse of tree.json. Suggestion: a `withTree(workDir, (tree) => ...)` helper (returns error text when missing/unreadable) or at least load once per execute and pass down. Reduces I/O and unifies the failure wording.

## 3. Over-complex functions

### 3.1 [HIGH] `log_experiment` execute is ~620 lines
`index.ts:5614-6230`. It interleaves eight concerns: gating, provenance, secondary-metric validation, ASI assembly, run-number minting, confidence/noise text, git commit, ledger+sidecar append, tree finalize, idea cleanup, auto-revert, steer hooks. Nesting reaches 5 in the confidence text block (5928-5970). Suggestion: extract pure helpers that already have natural seams — `validateLogInputs(params, state)`, `metricProvenanceOf(params, runtime, state)`, `assembleAsi(params, workDir, linkNodeId)`, `commitKeep(workDir, experiment)`, `appendLedgerWithSidecar(workDir, jsonlLine, runtime, runNumber)`, `revertNonKeep(workDir, status)`. The execute keeps only orchestration + response text assembly. No behavior change, big readability win, and each helper becomes unit-testable without the fake-pi harness.

### 3.2 [MED] `run_experiment` execute is ~740 lines with an inline 130-line spawn closure
`index.ts:4836-5580`; the spawn promise (5110-5245) handles buffering, truncation caching, timers, abort, and error paths inline. The chunk-eviction/UTF-8-boundary logic (5160-5180) is subtle and deserves its own module (`run-spawn.ts`) with focused tests (multi-byte char across chunk boundary, abort-before-spawn, timeout+close race). Suggestion: extract the whole Promise constructor into `spawnCaptured({command, cwd, timeoutMs, env, signal, sink, onUpdate})`.

### 3.3 [MED] `reconstructState` mixes three responsibilities
`index.ts:3116-3340`: (a) stale-tree cleanup (dangling run_started scan, 3130-3190), (b) state reconstruction from jsonl/session-history, (c) mode auto-activation. The dangling-run scan re-parses the entire ledger line-by-line with inline JSON.parse — this same "run_started without run_result" pairing exists conceptually in run-links.ts. Suggestion: extract `reapStaleRunningNodes(workDir)` and, if practical, share the started/result pairing logic with run-links' marker scan.

### 3.4 [LOW] Flag-shaped `isReinit`/`sameConfig` flow in init_experiment
`index.ts:4050-4080`: the resume-vs-resegment decision is a chain of boolean comparisons inline. Extracting `isSameTargetConfig(state, params, previousAnalysis, plannedAnalysis)` would make the resume rule readable and testable; it is currently only testable through the full tool call.

## 4. Business-logic holes

### 4.1 [HIGH] `log_experiment` noise-floor warning compares against a field that is always undefined
`index.ts:5944` filters `r.runNumber !== experiment.runNumber` — but `ExperimentResult` (index.ts:254-270) has **no `runNumber` field** (the ledger number lives only on the jsonl entry as `run`, and the in-memory object never gets it). `r.runNumber` is `undefined` for every result, and `experiment.runNumber` is also `undefined`, so `undefined !== undefined` is `false` — the filter is a no-op and `prevBest` **includes the run currently being logged**. Consequence: on a keep, "improvement vs prevBest" can be computed against itself, so `improvement === 0` and the within-noise warning silently never fires when it should (or fires with a self-comparison). Not a data-corruption bug (the ledger is fine), but the guard's advertised behavior is dead code. Suggestion: set `experiment.runNumber = runNumber` before this block, or filter by object identity (`r !== experiment`). Verify with a regression test: log a keep whose metric equals the previous best → warning must appear.

### 4.2 [MED] Inconsistent gate ordering between run/log — research gate placed differently
`run_experiment` (4870-4879): modeGate → workDir validation → campaign gate → research gate. `log_experiment` (5620-5636): modeGate → campaign gate (guarded by workDir-valid) → research gate → … → workDir validation **again** at 5636. In run_experiment the workDir error wins over the campaign block; in log_experiment the campaign block wins (it's pre-validated). Functionally close, but the duplicated `validateWorkDir` in log_experiment (once at 5621 inside the condition, once at 5636) is confusing and invites divergence. Suggestion: unify both tools on one order: modeGate → validateWorkDir → campaign → research → optimize, extracted into a shared `ordinaryLoopGate(ctx)` helper returning a refusal or null.

### 4.3 [MED] Auto-revert is fail-open with only a text note
`index.ts:6145-6170`: if the revert script fails (e.g. git lock, bad pathspec on an old git), the response says `⚠️ Git revert failed` and **the loop continues with the dirty tree**; the next experiment's baseline is then measured on mutated code. There is no runtime flag (`runtime.lastRevertFailed`) and no hook into the observer, so nothing downstream knows. The keep path is equally fail-open (commit failure → text note, keep recorded without a commit sha). Suggestion: at minimum record `runtime.lastRevertFailure` and re-warn on the next run_experiment response ("previous discard left a dirty tree — git status before trusting this baseline"); the honest-metric machinery already has the pattern (`lastLogFlag`) to copy.

### 4.4 [MED] Fallback run number in `log_experiment` can silently skip run-links
`index.ts:5795-5806`: when there was no in-session run_experiment, `runNumber` is computed as `max(ledgerMax, highestRunDir)+1` and the pending identity reset only happens `if (runtime.runLinks.pending !== null && pending.run !== runNumber)`. If the pending identity happens to match the computed fallback number, a link from a *different, never-run* execution would bind to a fabricated number — the code comments say a fallback "never proves a link", but the guard resets only on mismatch. An exact collision is unlikely but the invariant deserves an unconditional reset on the fallback path. Suggestion: `if (!runtime.lastRunNumber) runtime.runLinks = resetRunIdentities(...)` before computing the fallback.

### 4.5 [LOW] Secondary-metric "new metric" gate only fires after the first run established the list
`index.ts:5685-5705`: when `state.secondaryMetrics.length === 0` (first log), any metric names are accepted silently; from the second log on, unknown names require `force`. That's intended, but the `force` escape hatch writes the new metric into the epoch's baseline set permanently (registered at 5813-5825) — there is no way to un-track a wrongly forced metric except re-init. Suggestion: document, or provide removal via config. Low priority.

### 4.6 [LOW] `findBestRunNumber` index math assumes results array == segment run order
`index.ts:1389-1390`: `bestIdx >= 0 ? bestIdx + 1 : seg.length` — the "run number" is the position within the filtered segment array, which equals the ledger run number only if no runs were skipped/missing and no gaps exist. The ledger explicitly supports gaps (readLedgerMaxRun exists for that). The number is display-only ("set at run #N"), but it can name the wrong run. Suggestion: carry the real `run` number on the in-memory result (see 4.1) and display that.

## 5. Cohesion / extraction candidates

Ranked by leverage-to-risk:

1. **`ledger-metrics.ts`** (from 2.4): segment/epoch/baseline/confidence pure functions out of index.ts:841-950 — they are the shared vocabulary of index/report/observer/council/exhaustion-hints; centralizing kills three mirrors. Low risk (pure functions, existing tests cover them via tool paths).
2. **`git-ops.ts`** (from 2.2/4.3): `commitKeep`, `revertNonKeep`, baseline ref protection (init 4120-4130), tree git ops — all `pi.exec("git", ...)` call sites with their fail-open notes in one module with one error policy.
3. **`run-spawn.ts`** (from 3.2): the captured-spawn closure; independently testable.
4. **`log-response.ts`** or at least splitting the ~200 lines of response-text assembly (5750-5990) out of log_experiment's execute — it's pure (state, params, statuses) → string.
5. **Tree access layer** (2.5): `withTree` + single load per execute.
