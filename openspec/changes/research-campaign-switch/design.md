# Design: research-campaign-switch

## Контекст

Текущая механика (проверено по коду 2026-11-11):

- **Фазы кампании**: `briefing → research → stopped` (`research-state.ts:66`); `stopped` терминальна, схему валидирует `stateProblem` (`research-state.ts:543-557`).
- **Выход из активной фазы** только `research stop` (`index.ts:9824-9843`, transition через `updateState`) → `research report` (`index.ts:9592+`). Смерть сессии оставляет кампанию в `briefing`/`research` навсегда.
- **Guard запуска** (`index.ts:10453-10463`): `blockingCampaignIds` собирает кампании не-`stopped` фаз + нечитаемые; >1 → «Several campaigns exist…», 1 → «Campaign X is active…».
- **Атомарный протокол** `updateState` (`research-state.ts:589-618`): lock каталога → pending-op проверка → чтение (fail-closed) → decision → pending-op маркер → работа → запись состояния → снятие маркера. Сбой оставляет маркер (`operationFailed`, `research-state.ts:532`).
- **Replay журнала** (`index.ts:8720-8768`): события `open/record/close/stop`; неизвестное событие → `state_unreadable` (fail-closed). Значит событие `abandon` требует расширения replay.
- **Архив** (`index.ts:8540-8580`): `archiveFinishedCampaigns` переносит только `stopped`, move без delete; уже вызывается из draft (`index.ts:9307-9315`).
- **Nudges**: `RESEARCH_RESUME_TEXT` (`index.ts:2591`), drift-сообщения (`2594-2606`, `2640-2662`), лимит автопродолжений (`2440-2445`, `AUTORESUME_TURN_LIMIT` 292) — тексты статичны, состояния кампании не учитывают.
- **Charter-цепочки** (`chainCampaignIds`, `index.ts:8551`): кампании активной цепочки не архивируются; цепочка держит свой журнал статусов.

## Решения

### D1. Закрытие зависшей кампании — событие `abandon`, не новый механизм фаз

Не вводим фазу `suspended` (ранняя версия спеки) и не добавляем поля в `state.json`. Закрытие = append-only событие `abandon {reason: "stale"}` + transition `phase: research|briefing → stopped` через `updateState`. Это сохраняет: терминальность stopped, совместимость replay (расширяется одним событием), схему состояния, архив, тесты.

Альтернативы отклонены: sidecar-маркер паузы (вторая полуфаза без механизма возобновления, дублирует состояние); отдельная команда ручного закрытия без автозакрытия (владелец просил автоматизм при старте).

### D2. Признак «зависла» — «не закреплена за текущей сессией», без эвристики времени

Критерий закрываемости при guard'е (все обязательны):
1. фаза `briefing` или `research`;
2. **не** закреплена за текущей сессией (`runtime.researchCampaignId !== campaignId`);
3. каталог без `pending-op.json` (`researchState.PENDING_OP_FILE`);
4. `readState` читается и валидна;
5. id не входит в `chainCampaignIds(ctx)` активной цепочки.

Примечание: одобренный бриф с нарушенным хешем проходит критерии 1-5 (state.json валидна), но закрывается отказом на шаге 1 D3 — `researchSnapshot` → `checkBriefApproval` → `brief_changed` (index.ts:8789-8801). Фактически незакрываемая, запуск отказывает; fail-closed, соответствует существующей политике. В критерий не включена намеренно: проверка брифа и так выполняется при закрытии, дублирование в проходе guard'а не нужно.

Порядок проверок в launch-ветке кода: blocking-проверка (10453-10463) выполняется РАНЬШЕ pin-защиты (10474-10513) и делает `return`. Отсюда два наблюдаемых исхода для pinned-кампании в фазе briefing/research, оба СУЩЕСТВУЮЩИЕ (изменение не трогает ни один):
- запуск **без `--id`**: pinned-кампания остаётся в blocking-списке (она фаза ≠ stopped и лежит в bases через `pinnedStateRoot`), проход закрытия пропускает её по критерию 2 как незакрываемую → blocking-ветка отказывает существующим сообщением «Campaign X is active or unreadable; resume it … finish it first» (10459-10461);
- запуск **с `--id` другой кампании**: blocking-проверка пропускается (ветка --id, 10436-10452), срабатывает pin-защита «the pin is not replaced» (10501-10511).

Свойство, которое вводит изменение: pinned-кампания никогда не закрывается guard'ом (критерий 2 исключает её из прохода закрытия). Дизайн не меняет порядок кода; наблюдаемые отказы остаются прежними.

Сравнение «время последней активности < порога → не трогать» отклонено: тайминг-эвристика даёт ложные отказы (долгий research-ход) и ложные закрытия (мёртвая сессия «недавно» писала). Пин сессии решает конфликт двух живых окон: второе окно не закроет кампанию первого, пока первый не отпустит пин (`/autoresearch off`). Остаточный риск: две параллельные сессии без пинов — документируем, не решаем (см. Risks).

### D3. Порядок операций guard'а — закрытие до draft, атомарно по одной кампании

```
guard (launch, без --id):
  blocking = blockingCampaignIds(bases)
  для каждой blocking-кампании по очереди:
    если закрываемая (D2): closeStaleCampaign(dir)   // updateState: abandon + stopped
    иначе: отказ с перечнем незакрываемых и причин    // текущее поведение
  все закрыты → запуск продолжается (существующий flow, draft архивирует stopped)
```

`closeStaleCampaign`:
1. `researchSnapshot(dir)` — бриф, replay (для отчёта);
2. `updateState(dir, "abandon stale campaign", transition briefing|research→stopped, work: append {event:"abandon", reason:"stale"} + writeStaleReport)`;
3. отчёт пишется внутри `work` (внутри pending-op маркера): `report.md` из фактического состояния — метка «closed as stale (not completed)», открытые вопросы без вердиктов, хеши доказательств.

Briefing-кампания без одобренного брифа закрывается НАМЕРЕННО (решение владельца: запуск новой важнее сохранения черновика как возобновляемого): её отчёт включает черновик брифа дословно (`brief.json` читается с диска даже без approval — цель, вопросы, стоп-правила), так что содержимое черновика сохраняется в отчёте и архиве, хотя путь «подтвердить этот черновик позже» закрывается. Разделы статусов вопросов/стоп-срабатываний в таком отчёте отсутствуют (векторов нет).

После `abandon` журнальные события кампании недопустимы: replay отвергает ЛЮБОЕ событие (`open/record/close/stop`) после `abandon` как `state_unreadable` (fail-closed). Инструментальный слой и так отказывает: после stopped все действия требуют phase research (`inResearchPhase`, index.ts:9701+); правило replay закрывает подделку журнала вручную. Отказ закрытия любой кампании → отказ запуска, уже закрытые в этом проходе остаются `stopped` (корректно: они честно закрыты) и архивируются следующим draft.

### D4. Pin сессии и «already active» ветка не меняются

Ветка запуска с пином (`index.ts:10474-10513`) и ветка `--id` (`10436-10452`) не изменяются: явное `--id` на существующую кампанию — это осознанное возобновление, а не автозакрытие. Взаимная блокировка «пин на briefing-кампанию, хочет другую» остаётся прежней (`/autoresearch off` сбрасывает пин) — изменение этого поведения вне MVP.

### D5. State-aware nudges — тот же механизм автопродолжений, тексты по состоянию кампании

Механизм подталкивания уже работает во время кампании (автопродолжение при простое, drift-напоминания при пустых ходах); дефект в том, что тексты статичны: агент получает «Continue the research campaign: open/record/close» даже когда открытых вопросов нет — кампания никогда не подталкивается к завершению. Меняется только выбор текста, каналы доставки не трогаются:

- **Reply ветки close** (после успешного закрытия вопроса, ветка close-действия ~9759, reply ~9804): если после закрытия все вопросы брифа закрыты и стоп ещё не сработал — дописать строку «All questions are closed: pick a stop rule (research stop <rule_id>) then research report».
- **Композеры по состоянию (async)**: `composeCampaignResumeMessage` (2625), `composeDriftResumeMessage` (2640), `composeResearchDriftMessage` (2594, вызывается из 2644) читают snapshot pinned-кампании (researchSnapshot: replay журнала) и выбирают: открыты вопросы → текущий текст; все закрыты, стоп не сработал → «close the campaign (stop + report)». Ветка «стоп сработал → напиши отчёт» в композерах НЕ вводится: после `research stop` фаза становится stopped, `researchScanSync` помечает halted, напоминания не доставляются вовсе (fail-closed, см. следующий пункт) — такой WHEN недостижим; синхронный stop-reply уже указывает на отчёт (index.ts:9848). Async-композеры поддержаны существующим контрактом `ensurePendingResume` (`composeMessage?: → string | Promise<string>`), drift-путь уже awaited-композитит перед schedule (3333).
- **Pending-op / нечитаемое состояние — напоминание НЕ доставляется** (уже так сегодня): `ensurePendingResume` выходит до композера при `campaignNeedsManualCheck` (3253-3256), send-time проверка отменяет доставку (2430-2433) — это осознанный fail-closed (design §5 research-vectors: неясное состояние → стоп, оператор решает). Спека фиксирует это как требование БЕЗ изменения кода: nudge при незавершённой операции не доставляется вообще (доставка общего текста здесь была бы неверной — она подталкивала бы агента работать в состоянии manual_check_required).
- **Send-time override** (sendPendingResumeIfReady, 2451-2455): сейчас затирает сохранённый текст статичным RESEARCH_RESUME_TEXT при research-блоке — это перезаписало бы осведомлённый текст слепым. Заменить: затирать только legacy-цикловое сообщение (содержит run_experiment/log_experiment), state-aware сохранённый текст доставлять как есть.
- **Уведомление лимита** (notifyAutoResumeLimitReached, 2486; вызовы 2440, 2698, 3257, 3309): перед уведомлением snapshot кампании; завершена по вопросам, но фаза research → добавить «campaign <id> has all questions closed but is not finalized (needs stop + report)».

Чтение replay — один небольшой файл-чтение на напоминание (не на ход). Новых таймеров нет.

### D6. Что сознательно НЕ входит (MVP)

- Закрытие кампаний активной charter-цепочки (свой протокол статусов, `chain_stop` с диалогом владельца).
- Suspend/resume-фаза, параллельные кампании, ручная команда закрытия произвольной кампании.
- Автозакрытие по таймеру/возрасту (только в момент запуска новой кампании).
- Изменение `research stop`/`report` живой сессии, схемы `state.json`, формата архива.

## Риски

- **Две параллельные сессии без пинов**: обе считают чужую кампанию зависшей. Смягчение: закрытие идёт через `updateState` (lock + pending-op), одновременное закрытие одной кампании невозможно; вторая сессия увидит уже `stopped`. Окно «закрыли живую» остаётся при запуске второй сессии во время паузы первой — документируется (как существующая cross-session невидимость `--state-root`).
- **Briefing-черновик закрывается вместе с путём одобрения**: владелец больше не сможет подтвердить бриф зависшей briefing-кампании позже (принято владельцем 2026-11-11: запуск новой камеры важнее; содержимое черновика сохраняется в отчёте дословно, включая цель, вопросы и стоп-правила).
- **Одобренный бриф с нарушенным хешем** (`approvedBriefGuard` внутри `updateState`, research-state.ts:982-985, 602): закрытие отказывает — кампания незакрываемая, запуск отказывает (fail-closed, соответствует существующей политике brief_changed).
- **Нечитаемый log.jsonl у зависшей кампании**: снапшот отказывает → кампания незакрываемая → запуск отказывает (fail-closed, соответствует существующей политике).
- **Событие `abandon` и старые версии кода**: старый replay отвергнет журнал с `abandon` как повреждённый (fail-closed, состояние не теряется, но кампания «замораживается» для старого кода). Приемлемо: апгрейд атомарен с кампанией, downgrade-совместимость не требуется.
- **Отчёт как «честный»**: агент-владелец данных не участвует в генерации отчёта — это машинный срез состояния. Спека прямо запрещает вердикты и утверждения завершения.

## Тестовая стратегия (проверяемость сценариев)

- Закрытие зависшей research-кампании: журнал содержит `abandon`, фаза stopped, отчёт с меткой и открытым вопросом без вердикта; затем draft архивирует её и создаёт новую (расширить `tests/research-exit-archive-fixes.test.mjs`).
- Незакрываемые: pending-op → отказ запуска, ничего не изменено; нечитаемый state → отказ (существующий сценарий сохраняется); кампания цепочки → отказ, журнал цепочки не тронут.
- Атомарность: сбой записи внутри закрытия → pending-op остаётся, повторный запуск отказывает с manual_check_required.
- Идемпотентность: вторая попытка закрытия stopped-кампании → отказ, второго `abandon` нет.
- Replay: журнал с двумя `abandon` / `abandon` после `stop` → `state_unreadable`.
- Pin-защита: кампания, закреплённая за сессией, не закрывается guard'ом (проверка «already active» ветки).
- Nudges: закрытие последнего вопроса содержит подсказку stop/report; автопродолжение при всех закрытых вопросах предлагает stop+report и не предлагает open; при pending-op/нечитаемом состоянии и фазе stopped напоминание НЕ доставляется (проверка раннего выхода ensurePendingResume и send-time отмены); лимит автопродолжений называет незакрытую кампанию.
- Регресс: headless-launch сценарии guard'а (204-232 в существующей спеке) в новых редакциях.
