# Дизайн: исследовательская кампания по векторам (research-vectors)

**Статус:** черновик rev.3, ожидает независимого ревью по `plan-loop`. Реализации нет.

## 1. Идея простыми словами

Кампания `research` не ищет лучшее число. Она отвечает на заранее записанные вопросы. Всё, что можно решить до запуска (вопросы, правила ответа, стоп-правила, план), записывается в **бриф**. Владелец подтверждает бриф один раз. Потом агент работает сам и закрывает вопросы по правилам из брифа. Изменить бриф после подтверждения нельзя.

## 2. Две фазы

```
Фаза 1: research_brief(draft) → research_brief(propose) → диалог владельца (ctx.ui.confirm === true)
        → approval.json с SHA-256 брифа
Фаза 2: research(start, brief_sha256=…) → проверка хеша → векторы → closure → report
```

- Фаза 1 интерактивна. Без UI подтверждение невозможно, поэтому бриф не вступает в силу.
- По согласованному брифу формируется промпт запуска с путём и ожидаемым хешем брифа; он передаётся в фазу 2. Если хеш файла не совпал с `approval.json` или с ожидаемым, действия исследования отказывают с `brief_changed`, и кампания ждёт ручной проверки.
- Один бриф — одна кампания. Новая кампания создаётся в отдельном каталоге со своим брифом и подтверждением; прежние записи сохраняются. При подтверждении диалог показывает содержание брифа и его хеш.

## 3. Хранилище (без git)

Каталог кампании `<workDir>/.auto/research/<campaign_id>/` (у каждой кампании свой идентификатор):

| Файл | Содержимое | Кто пишет |
|---|---|---|
| `brief.json` | Вопросы, правила, роли данных, стоп-правила, план-источник, блок ограничений | фаза 1, до подтверждения |
| `approval.json` | SHA-256 `brief.json`, время, факт подтверждения `true` | только после `ctx.ui.confirm` |
| `state.json` | Фаза кампании и её идентификатор | инструменты режима (атомарная запись tmp+fsync+rename) |
| `log.jsonl` | Append-only журнал: открытия и закрытия векторов, доказательства, стоп, отказы — источник истины по векторам | инструменты режима |
| `lock.json` | Эксклюзивная блокировка (`wx`), без авто-снятия | инструменты режима |
| `pending-op.json` | Маркер незавершённой операции | инструменты режима до и после записи |

Находки (`record_finding`) остаются в `.auto/findings.jsonl` и ссылаются по `id`.

## 4. Формат брифа (`brief.json`)

```json
{
  "schema_version": 1,
  "goal": "текст цели, одно предложение",
  "plan_source": "путь или описание плана, задаётся при запуске",
  "caveat_block": "обязательный текст ограничений (дословно из протокола)",
  "data_roles": { "explore": ["данные для исследования"], "validate": ["данные для проверки"], "confirm": [] },
  "questions": [
    {
      "id": "Q1",
      "text": "вопрос простыми словами",
      "decision_rules": [
        { "id": "Q1-yes", "verdict": "confirmed", "when": "текст условия" },
        { "id": "Q1-no", "verdict": "rejected", "when": "текст условия" },
        { "id": "Q1-unknown", "verdict": "inconclusive", "when": "текст условия" },
        { "id": "Q1-wait", "verdict": "waiting_for_data", "when": "необходимые данные недоступны" }
      ],
      "needs_data": "описание или null"
    }
  ],
  "process_metrics": ["показатели, необходимые конкретному исследованию"],
  "stop_rules": [
    { "id": "S1", "when": "два подряд закрытых вектора как rejected без новых данных" }
  ]
}
```

Допустимые вердикты: `confirmed`, `rejected`, `inconclusive`, `waiting_for_data`. Правила ответа записаны текстом. Инструменты проверяют структуру и ссылки, но не вычисляют условия автоматически.

## 5. Инструменты

Один инструмент `research_brief` для фазы 1 и один `research` для фазы 2, оба с действиями:

- `research_brief`: `draft` (создать или изменить черновик, пока нет `approval.json`), `propose` (диалог владельца), `status`.
- `research`: `start` (проверка хеша, переход в фазу 2), `open` (вектор по `id` вопроса из брифа), `record` (доказательство), `close` (вердикт по `rule_id`), `stop` (стоп-правило), `status`, `report`, `resolve` (ручное восстановление после проверки). `status` и `report` доступны после остановки.

Инструмент не принимает поля подтверждения от модели: лишние ключи отклоняются, а подтверждение принимается только через `ctx.ui.confirm`. Файлы состояния доступны обычным файловым инструментам агента: подтверждение защищено на уровне инструмента, а не от прямой подделки файлов; агенту запрещено их подделывать.

## 6. Закрытие вектора

1. `open`: вопрос из брифа, нет другого активного вектора, режим фазы 2 активен.
2. `record`: вывод с `evidence_ref` (`путь:строки` или `путь#якорь`). Инструмент считает SHA-256 файла и пишет его в журнал. Это позволяет обнаружить изменение файла, но не доказывает воспроизводимость исследования.
3. `close`: вердикт и `rule_id`, который обязан существовать в брифе для этого вопроса и совпадать с вердиктом. Для `inconclusive` и `waiting_for_data` нужна причина. Журнал сохраняет текст вопроса и применённого правила.
4. Закрытый вектор не переоткрывается. Повторный вопрос — только через новый бриф.

Если бриф требует независимых подтверждающих данных, а их нет, вопрос получает `waiting_for_data`, а не `confirmed`. Применение правила (то, что условие «выполнено») остаётся суждением агента. Инструмент проверяет только, что агент выбрал существующее правило и приложил доказательство. Автоматической проверки условия нет. Это компромисс ради простоты и честного описания.

## 7. Процессные метрики

`research(status)` и `research(report)` показывают статусы вопросов и проверяют сохранность записанных доказательств. Другие показатели и проверки задаются брифом для конкретного исследования и отражаются агентом в отчёте; система не выдаёт непроверенные сведения за вычисленные факты. Целевой метрики кампании нет.

## 8. Блокировки и режимы

- Под активным режимом `research` блокируются: `init_experiment`, `run_experiment`, `log_experiment`, `propose_hypothesis`, `finalize_research`, `/autoresearch parallel-*`, `finalize` и `council`, а также `candidate_branch` и инструменты совета `council_*`. Причина: ordinary-loop и кандидаты пишут в git; совет в MVP не адаптирован к этому режиму.
- Инструменты чтения и записи заметок (`inspect_results`, `tree_status`, `record_finding`, `update_finding`, `log_observation`) остаются открыты.
- Инструменты измерения и анализа (`log_measurement_change`, `verify_measurement_change`, `revert_measurement_change`, `record_analysis`, `direction_review`) и поиска прецедентов (`search_precedents`, `assess_precedents`) остаются открыты. Совет и его инструменты в MVP заблокированы: их совместимость с режимом отдельно не определена.
- Агенту запрещены Git-операции, в том числе через оболочку. Инструменты расширения не вызывают Git; несовместимые пути блокируются. Интеграция блокирует прямые вызовы Git через доступный перехват команд Pi; тесты проверяют запрет и отсутствие внутренних вызовов. Это не песочница ОС: произвольный дочерний скрипт или внешние процессы технически не контролируются; защита от них не обещается.
- Промпт, подсказки, автоматическое продолжение и уведомления о простое учитывают режим `research`: не направляют в обычный цикл. Вызовы инструментов исследования учитываются как работа, а не простой; при остановке или необходимости ручной проверки автоматическое продолжение не запускает работу. Режим обеспечивает доступность разрешённых инструментов заметок и работу перехвата команд.

## 9. Отказы и восстановление

- Незавершённая операция → `pending-op.json` → `manual_check_required`. Агент останавливается и сообщает. После проверки оператор может через `research(resolve)` подтвердить снятие маркера; без UI или при отказе маркер сохраняется. Это защита через инструмент, не от прямой правки файлов.
- Повреждённый `state.json` или `brief.json` → фаза блокируется (fail-closed), обычный цикл не разблокируется; требуется ручная проверка и восстановление оператором, не автоматический ремонт.
- Изменение брифа после подтверждения → `brief_changed`, всё блокируется до ручной проверки.

## 10. Что не делаем в MVP

- Автоматическое вычисление условий правил.
- Узкий git-режим (отложен, отдельное решение).
- Сбор новых данных.
- Любые вычисления статистики внутри инструментов: эта работа выполняется скриптами исследования и попадает в журнал как доказательство.

## 11. Решения MVP

Правила текстовые, их применение оценивает агент; отдельный механизм вычисления правил не требуется. Для подтверждения используется один диалог с брифом и хешем. Отчёт выдаёт `research(report)`.
