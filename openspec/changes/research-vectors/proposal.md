# Proposal: Исследовательская кампания по векторам (research-vectors)

**Статус:** черновик rev.2. Документы проходят ревью; ничего не реализовано.

## Why

Текущая кампания работает только с одной числовой метрикой: `init_experiment` требует `metric_name`, `log_experiment` требует числовой `metric`, статусы `keep`/`discard` опираются на лучший результат. Для исследовательских задач без целевой метрики (качество данных, реакция стакана, повторяющиеся ситуации, проверка чужих выводов) эта модель не подходит: приходится выдумывать прокси-метрику, а это противоречит цели честного ответа на вопрос.

## Решения владельца (зафиксированы)

1. Вид кампании `research` в pi-autoresearch — **да**.
2. Агент сам закрывает вопрос (вектор) по заранее записанному правилу — **да**. Владелец не участвует в ходе работы.
3. Лимита времени или токенов на отдельный вопрос **нет**.
4. Git-операции в виде `research` **запрещены** на текущем этапе. Узкий git-режим (явный список путей) отложен до отдельного решения; без git работаем через манифест хешей.
5. Подтверждающие данные: если новых дней нет, вопрос получает статус «ждём данных» и не подтверждается на старых данных. Детализация кейсов сбора данных не входит в этот change.
6. Какой план использовать для конкретного проекта — **не фиксируется в коде**; задаётся в брифе при запуске.

## Двухфазный запуск (новое требование владельца)

**Фаза 1. Согласование брифа.** Интерактивная. Агент вместе с владельцем уточняет цель, список вопросов, для каждого вопроса — решающее правило («да / нет / не знаем»), роли данных (исследование, валидация, подтверждение), процессные метрики, стоп-правила и источник плана. Результат — файл брифа с SHA-256. Бриф начинает действовать только после подтверждения владельцем через диалог (`ctx.ui.confirm` строго `true`). Модель не может подтвердить бриф сама.

**Фаза 2. Исследование.** Кампания запускается с путём и хешем брифа. Она проверяет хеш и читает вопросы и правила только из брифа. Агент сам открывает вектор, работает, записывает вывод с доказательством и закрывает вектор по правилу. Добавлять или менять вопросы в фазе 2 нельзя: для этого нужна новая фаза 1. Владелец получает итоговый отчёт.

## Что меняется

- Новый вид кампании `research` с собственным состоянием: список векторов, один активный вектор, журнал закрытий.
- Закрытие вектора только по правилу из брифа: `confirmed`, `rejected`, `inconclusive` (с причиной) или `waiting_for_data`. Обязательная ссылка на доказательство.
- Вместо целевой метрики — статус вопросов и проверка сохранности записанных доказательств. Другие показатели и проверки определяются брифом и описываются в отчёте, если применимы.
- Переиспользование подходящих существующих частей: находки с `evidence_ref`, механизмы состояния и блокировки инструментов под режимом.
- Git-операции в режиме `research` не выполняются. Откаты и коммиты не вызываются.

## Что не входит

- Оптимизация числа и поиск лучшего результата.
- Торговля и оценка P&L.
- Изменение существующего цикла `run_experiment`/`log_experiment` и кампаний кандидатов.
- Узкий git-режим (отложен).
- Сбор новых данных и конкретные кейсы сбора (отдельный вопрос).
- Выбор плана для конкретного проекта (задаётся в брифе).

## Impact

- Новые файлы: модуль состояния `research` и инструменты фаз 1 и 2 в `extensions/pi-autoresearch/`.
- Тесты: переходы состояния, проверка хеша брифа, отказ без подтверждения, отсутствие git-вызовов (тест с мутацией), закрытие по правилу, отказ при изменении вопросов в фазе 2.
- Документация и промпт: краткое описание режима, без упоминания заблокированных инструментов в тексте режима `research`.

## Следующие шаги

1. `design.md`: состояние, формат брифа, инструменты, граница между фазами.
2. `specs/`: требования и сценарии.
3. `tasks.md`: задачи с зависимостями; реализация только после согласования по OpenSpec-гейту.
4. Независимое ревью документов свежим агентом по протоколу `plan-loop`, до вердикта ГОДЕН.
