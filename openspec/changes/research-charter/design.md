# Design: research-charter (MVP)

Ревизия: rev.3 (цикл ревью, раунды 1–2; решение владельца — цепочка по умолчанию без лимитов). Уровень деталей — MVP. Поведение и инварианты зафиксированы в спеке; здесь только ключевые решения и их причины.

## Решения

1. **Источник истины — хеш из аргументов запуска; диалог — чтение, не ввод.** В headless-режиме ожидаемый хеш хартии приходит от владельца в аргументах, и агент не может подменить одновременно файл и хеш. В интерактивной сессии модель может передать только путь хартии; система сама вычисляет SHA-256, показывает владельцу диалог, первая строка которого `Charter SHA-256: <hex>`, дальше — сводка полей хартии, и пере-хеширует файл в момент подтверждения (прецедент: `writeOptimizeApproval` в optimize-brief.ts повторно читает и хеширует бриф перед записью подтверждения; диалог брифа начинается с `Brief SHA-256: <hex>`). Диалог отвечает строго `true`. Канал диалога обёртки в headless считается интерфейсом владельца (это его аргументы и его ответ `true` при совпадении хеша), поэтому требование «Нет интерфейса» на headless-путь не распространяется. Поля одобрения от модели (`approved`, `confirmed`, `charter_sha256`, `operator_confirmation` и любые неизвестные поля вызова) отклоняются — allowlist параметров действия, как `APPROVAL_KEYS` в optimize-brief.ts.

2. **Хартия вне рабочей директории.** Проверяется по realpath (разворот symlink/junction, нормализация регистра Windows) относительно рабочего каталога запуска обёртки/сессии. Причина: агент с записью в рабочую директорию может переписать файл хартии; вне неё такой путь закрыт для инструментов расширения. Прямая запись через shell остаётся остаточным риском, как и раньше; она обнаружима сверкой хеша (`charter_changed`, задача 3.6). Отзыв хартии как отдельный механизм не нужен: остановка — `chain_stop`, изменение файла обнаруживается сверкой хеша.

3. **Автоподтверждение только механических проверок.** Инструмент проверяет: схему брифа; дословное равенство блока ограничений; **эффективный** набор вердиктов (родитель без поля `verdicts` и потомок с явно объявленным тем же набором совпадают — семантика поля из research-brief-gates); `evidence_gate` как объект (массивы — как множества, порядок не важен; оба отсутствуют = совпадение); ссылки каждого вопроса на **находку цепочки**; лимиты, если заданы. «Находка цепочки» — вопрос, закрытый **с доказательством** в любой кампании этой цепочки вердиктом из её эффективного набора (включая `waiting_for_data`); носитель ссылки — поле `finding_refs` вопроса брифа: массив пар `{campaign, question}`; проверка — каждая пара существует среди закрытых с доказательством вопросов журналов кампаний цепочки (источник истины — журналы кампаний, в `chain.json` пишется только снимок факта подтверждения). Носитель ссылки, формат хартии и состав снимка зафиксированы в спеке (§Состав хартии, §Журнал цепочки). Тексты правил закрытия вопросов между кампаниями не сравниваются (вопросы разные; инвариант цепочки — вердикты, `evidence_gate`, блок ограничений). Суждение «вопрос логично следует из находки» остаётся за агентом; темы вопросов владелец не ограничивает — это согласованное допущение (остаточный риск: агент порождает и сам находит ссылки, механика проверяет только существование и закрытость с доказательством).

4. **Журнал цепочки append-only с хеш-цепочкой и внешним якорем.** `chain.json` лежит в каталоге цепочки `<state-root>/research-chain/<id>/` — вне каталогов кампаний, поэтому архивация кампаний его не двигает. Каждая запись несёт `prev_hash`; головной хеш хранится **отдельно** от журнала (файл `chain-head` в том же каталоге), и это значение сверяется при каждом действии цепочки — согласованная подделка самого `chain.json` не проходит сверку с якорем. Состав записи подтверждения: хеш брифа, хеш хартии, снимок родителя (поля: `caveat_block`, эффективный набор вердиктов, `evidence_gate`, id кампании). Вердикты закрытых вопросов в `chain.json` не дублируются — источник истины для проверок ссылок: журналы кампаний (событие `close` с вердиктом, правилом и доказательством). Расхождение якоря, повреждение или отсутствие `chain.json` при действии цепочки → `manual_check_required`.

5. **Режим между кампаниями выключается только отчётом; `chain_stop` и стоп-правило хартии в паузе — немедленное выключение.** Промежуточный отчёт сохраняет режим и отправляет агенту одно продолжение к брифу следующей кампании; повторного продолжения без нового действия агента нет. Автоподтверждение дочернего брифа возможно только после записанного отчёта родителя (статус `awaiting_child`) — бриф, отправленный раньше, отклоняется (`parent_not_reported`), что исключает создание дочерней кампании в окне «родитель остановлен до отчёта». Остановка кампании по стоп-правилу (`stop`) без отчёта режим не выключает — кампания цепочки обязана написать отчёт по общему правилу research-vectors, и только он выключает режим. Исключение, закрывающее тупик `awaiting_child`: в паузе отчёт последней кампании уже сохранён, поэтому `chain_stop` или стоп-правило хартии из паузы переводят цепочку в финальный статус и выключают режим немедленно — новый отчёт не требуется. Финальный отчёт кампании цепочки в фазе `research` после `chain_stop` (стоп-правило/лимит во время активной кампании) выключает режим как отчёт «последней кампании» — это исключение из правила «Отчёт незавершённой кампании режим не меняет» (вне цепочек), зафиксированное в теле MODIFIED-требования.

6. **Команда владельца `research chain_stop`.** Диалог оператора (как у `resolve`: разрешение явно, модель не может подтвердить за владельца) переводит цепочку в `stopped_by_owner`. Действие останавливает создание новых кампаний; работа открытого вектора активной кампании не прерывается. Семантика по состояниям: из `active` — кампания завершает работу по правилам research-vectors (закрытие векторов, `stop`, финальный отчёт, который выключает режим как отчёт последней кампании); из `awaiting_child` — режим выключается немедленно (решение 5). Выход из `awaiting_child` к продолжению цепочки — только новое действие агента (бриф); автопродолжений простоя в паузе нет.

7. **Headless-обёртка: контракт аргументов.** `--charter <путь>` требует `--approve-charter-sha <hex 64 нижний регистр>`: отсутствие одного из них — ошибка разбора аргументов (как текущая ошибка «--approve-sha is required»), до запуска pi и без создания состояния. С `--charter` обёртка распознаёт диалог `Charter SHA-256:` отдельной регуляркой (префикс не пересекается с `Brief SHA-256:`) и отвечает `true` только при совпадении с `--approve-charter-sha`; несовпадение — ответ `false` (диалог отклонён) и, поскольку хартия не принята, код выхода 3 без создания какого-либо состояния; корневой бриф требует обычного подтверждения (`--brief` + `--approve-sha` как сейчас) — первый бриф подтверждает владелец, автоподтверждаются только последующие брифы цепочки. Промежуточный отчёт цепочки не завершает запуск: обёртка доставляет продолжение и ждёт следующего действия агента. Если агент встал в `awaiting_child` (ход завершён без нового брифа) — штатный выход с кодом 0, состояние на диске сохраняется; `chain_stop` в headless недоступен, владелец останавливает цепочку в интерактивной сессии или новым запуском. Идентификаторы кампаний цепочки назначает система (`<chain-id>-c<номер>`, нумерация с первой дочерней; корневая кампания сохраняет свой id); идентификатор корня известен агенту из продолжения. Агенту запрещено передавать campaign_id — как и сейчас. Поведение без `--charter` прежнее; коды выхода существующих сценариев не меняются.

## Не делаем в MVP

- Отдельный интерфейс для просмотра цепочки (достаточно `chain.json`).
- Автоматическое переформулирование вопросов или выбор вопросов по весу находок.
- Бюджет по токенам и времени; лимиты кампаний/глубины — опциональны, по умолчанию выключены (решение владельца 2026-11-10).
- Изоляция журнала от файловых инструментов (хеш-цепочка с внешним якорем даёт обнаружение, не защиту; shell-подделка — остаточный риск, как для state.json).
- Механическая проверка стоп-правил хартии: правила хартии самоотчётные, агент отмечает выполнение; система не верифицирует условия — принято как остаточный риск.
- Отдельная команда отзыва хартии; отдельный headless-механизм `chain_stop`.

## Открытые вопросы для ревью владельца

- Лимиты по умолчанию выключены (решение владельца 2026-11-10); при необходимости включаются полями `max_campaigns`/`max_depth` в хартии. Глубина корня = 0; при линейной цепочке глубина = число кампаний − 1, поэтому без лимитов оба поля эквивалентны и достаточно одного — оставить оба на будущее ветвление или сократить до `max_campaigns`, решить при включении лимитов.
- Признано допущением владельца по умолчанию (не вопрос): ссылки вопросов на находки проверяются механически, но находки порождает сам агент; темы вопросов владелец не ограничивает. Возражение = правка требования «Автоподтверждение брифа цепочки» до запуска реализации.
