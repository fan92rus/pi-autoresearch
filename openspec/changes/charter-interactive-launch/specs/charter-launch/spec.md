# Spec Delta

## Purpose

Способность `charter-launch`: двухфазное интерактивное согласование хартии исследовательской цепочки (черновик агента → диалог владельца с хешем) и немедленный запуск цепочки из одной команды `/autoresearch charter`, при сохранении всех гарантий research-charter (привязка одобрения к байтам файла, перечитывание файла на каждом действии цепочки, единственность активной цепочки).

## ADDED Requirements

### Requirement: Двухфазное формирование хартии

Система SHALL предоставлять команду `/autoresearch charter <описание>` с двумя фазами. Фаза draft: инструмент `research_charter` с действием `draft` принимает от агента только объект хартии и валидирует его по правилам состава research-charter (`validateCharter`: allowlist полей, лимиты, стоп-правила); черновик — данные сессии в памяти, MUST NOT создавать журнал, кампанию, файл или research-режим; отказ валидации возвращает именованную причину и ничего не меняет. Фаза propose: действие `propose` сериализует черновик канонически (`JSON.stringify(obj, null, 2) + "\n"`), показывает владельцу диалог с первой строкой «Charter SHA-256: <hex>» от хеша этой сериализации; подтверждение — только явное строго `true` владельца. Модель MUST NOT передавать в вызовы инстру поля одобрения (`approved`, `confirmed`, `owner_confirmed`, хеши) — вызов с ними отклоняется. Перезапуск pi теряет черновик (остаточное поведение: владелец начинает команду заново).

#### Scenario: Черновик не проходит состав

- **WHEN** агент вызывает `research_charter draft` с хартией, отклоняемой `validateCharter` (неизвестное поле, лимит ниже порога, недопустимое стоп-правило)
- **THEN** система отказывает с именованной причиной, перечисляющей проблемы; черновик, журнал, кампания, файл и режим не создаются

#### Scenario: Модель передаёт одобрение

- **WHEN** в вызове `draft` или `propose` присутствует любое поле вне действия (в том числе поля одобрения или хеши)
- **THEN** вызов отклоняется, хартия не фиксируется

#### Scenario: Диалог и фиксация

- **WHEN** агент вызывает `research_charter propose` после успешного draft и владелец отвечает строго `true` в диалоге «Charter SHA-256: <hex>»
- **THEN** система выполняет фиксацию-запуск по требованию «Фиксация-запуск»

#### Scenario: Владелец отказал

- **WHEN** владелец отвечает иначе, чем строго `true`, или диалога нет (`ctx.hasUI = false`)
- **THEN** ничего не записывается и не запускается; черновик сохранён, повторный `propose` возможен

#### Scenario: Повторный propose после фиксации

- **WHEN** агент повторно вызывает `propose` после уже успешной фиксации-запуска, а новый черновик не создан
- **THEN** система возвращает запись первой фиксации (хеш, путь, id цепочки) и не создаёт вторую цепочку; это правило имеет приоритет над отказом при активной цепочке: записи состояния не меняются, диалог не показывается. Активная цепочка отказывает только `draft` и `propose` с живым черновиком

#### Scenario: Новый draft заменяет черновик

- **WHEN** агент вызывает `draft` при незафиксированном черновике
- **THEN** черновик и его показанный хеш заменяются; фиксация возможна только из последнего черновика

### Requirement: Конфликты состояния

Система MUST проверять конфликты дважды: при входе в команду и непосредственно в `propose` перед записью файла. Запуск `/autoresearch charter` MUST отказывать с именованной причиной без создания черновика, если в сессии активна цепочка или research-кампания (с цепочкой или без). Если конфликт возник между входом в команду и propose (например, кампания стартовала в другом ходе), propose отказывает, файл не пишется. Инструмент `research_charter` при активной цепочке отказывает целиком (кроме возврата записи первой фиксации по сценарию «Повторный propose после фиксации») — черновик не может повлиять на запущенную цепочку.

#### Scenario: Активная цепочка или кампания

- **WHEN** `/autoresearch charter` вызван при активной цепочке или активной research-кампании
- **THEN** команда отказывает с именованной причиной; черновик, журнал, кампания и файл не создаются

#### Scenario: Новый запуск при живом черновике

- **WHEN** `/autoresearch charter` вызван при незавершённом черновике хартии (без активной цепочки или кампании)
- **THEN** команда открывается заново: агент формирует новую хартию, новый draft заменяет старый черновик (spec «Двухфазное формирование хартии»); отказов для живого черновика нет

### Requirement: Фиксация-запуск

Фиксация SHALL быть одной атомарной операцией «записать → запустить» без промежуточных фиксируемых состояний. При `true` владельца система: (1) проверяет конфликты (см. «Конфликты состояния»); (2) записывает сериализацию черновика в файл с эксклюзивным созданием (wx) за пределами рабочего каталога, realpath которого не лежит внутри него; имя файла детерминировано из корня цепочки и метки времени; перезапись существующего файла запрещена — коллизия имени влечёт отказ `charter_path_taken` без запуска; (3) перечитывает файл с диска и сверяет хеш с показанным; расхождение или ошибка чтения — отказ `charter_changed`, записанный файл удаляется; (4) пиннит корневую кампанию: id из `--id`, иначе сгенерированный системой id формата `bench-<метка времени>` по правилам draft research-кампаний; (5) создаёт журнал цепочки `<корень>-chain`; (6) фиксирует путь и хеш хартии в состоянии сессии, включает research-режим и отправляет бриф-кикофф — изменения runtime, режима и отправка кикоффа составляют последний шаг и после него отказов не предусмотрено: отправка кикоффа — постановка сообщения в очередь отправки (внутренний вызов без внешних зависимостей, не способная отказать по внешней причине). Целевой путь файла вычисляется до шага 4. Если шаги 4–5 отказывают (например, `campaign_exists`, отказ `createChain`), система откатывает всё, что успела создать на упавших шагах: удаляет записанный файл хартии, каталог созданной кампании и каталог журнала цепочки (оба созданы только что этой операцией), не изменяет runtime-состояние и не включает режим; фиксация не сохраняется, владельцу сообщается именованная причина — состояние отсутствует, повторная команда начинает заново. После успешной фиксации-запуска черновик очищается; дальнейшее поведение цепочки (диалог корневого брифа, автоподтверждение детей, отчёты, chain_stop, перечитывание файла хартии на действиях) идёт по существующим требованиям research-charter.

#### Scenario: Один вход до бриф-диалога

- **WHEN** владелец подтвердил хартию и шаги записи и запуска прошли
- **THEN** журнал цепочки создан, research-режим включён, бриф-кикофф отправлен; следующий диалог владельца — корневой бриф («Brief SHA-256»)

#### Scenario: Указан id корня

- **WHEN** владелец вызвал `/autoresearch charter --id c1 <описание>` и подтвердил хартию
- **THEN** корневая кампания пиннится как `c1`, цепочка получает id `c1-chain`

#### Scenario: Коллизия пути файла

- **WHEN** файл по целевому пути уже существует
- **THEN** фиксация-запуск отказывает с `charter_path_taken`; существующий файл не перезаписывается, состояние не создаётся

#### Scenario: Расхождение после записи

- **WHEN** хеш перечитанного файла не равен показанному хешу, или файл не читается
- **THEN** отказ `charter_changed`, записанный файл удаляется, состояние не создаётся

#### Scenario: Запуск не удался после записи

- **WHEN** запись прошла, а создание кампании или журнала отказало
- **THEN** система откатывает созданное: удаляет файл хартии, каталог кампании и каталог журнала цепочки, созданные этой операцией; runtime и режим не изменены; фиксация не сохраняется, состояние отсутствует, владельцу сообщена именованная причина

#### Scenario: Конфликт возник между фазами

- **WHEN** к моменту `propose` в сессии появилась активная цепочка или research-кампания
- **THEN** `propose` отказывает, файл не пишется, черновик остаётся на месте

#### Scenario: Файл подменён после запуска

- **WHEN** файл хартии изменён после успешной фиксации-запуска
- **THEN** следующее действие цепочки отказывает с `charter_changed`, цепочка переходит в `manual_check_required` (по требованиям research-charter)
