# Design

## Context

Спека research-charter заморожена (rev.4) и реализована: запуск цепочки идёт через `/autoresearch research --charter <путь> --id <корень>`, где хартия — уже существующий файл за пределами рабочего каталога, одобренный диалогом `acceptLaunchCharter` (первая строка «Charter SHA-256: <hex>»); launch-ветка без `--id` отказывает (review B3). Модули: `extensions/pi-autoresearch/charter.ts` (валидация, диалог), `chain-journal.ts` (createChain), `index.ts` (launch-ветка `requestedCharterPath`). Двухфазные образцы: research_brief draft → propose, optimize_brief. См. proposal.md (Why).

## Goals

- Один вход: `/autoresearch charter [описание] [--id <корень>]` — от разговора до работающей цепочки.
- Переиспользование: `validateCharter`, диалоговый формат, `createChain`, launch-код.
- Все гарантии research-charter сохраняются: перечитывание файла на действиях цепочки, `charter_changed`/`manual_check_required`, привязка одобрения к байтам.

## Non-Goals

- Параллельные цепочки; редактирование принятой хартии командой; headless-флаги для команды (обёртка остаётся на `--charter/--approve-charter-sha`); изменение текста замороженных требований research-charter.

## Решение 1: Носители фаз — команда и инструмент

`/autoresearch charter <описание>` — подкоманда существующей slash-команды (рядом с `research`). Она ставит в runtime флаг «диалог о хартии» (`charterDialogOpen = true`), включает autoresearch-режим НЕ сразу (режим включается только при запуске цепочки, задача 3.1), и отправляет агенту инструкцию собрать рамки по словам владельца. Агент вызывает новый инструмент `research_charter`:

- `research_charter draft { charter }` — allowlist параметров: только `charter`; валидация `validateCharter`; черновик `{ charter, shownSha256 }` в runtime-состоянии сессии. Гейт: инструмент отвечает отказом, если `charterDialogOpen !== true` (вне диалога о хартии недоступен) или если активна цепочка.
- `research_charter propose` — без параметров модели вовсе (кроме, возможно, пустого объекта); сериализует черновик, показывает `ctx.ui.confirm` с `charterDialogText(charter, shownSha256)` (первая строка «Charter SHA-256:»), при строго `true` вызывает фиксацию-запуск. Порядок проверок внутри propose: (а) если запись о первой фиксации есть и черновика нет — вернуть запись (приоритет над отказом при активной цепочке; состояние не меняется); (б) иначе — конфликт-проверка; (в) — диалог.

Модель доверия: подтверждение живёт только в `ctx.ui.confirm`; вызовы инстру не содержат полей одобрения (та же модель, что acceptCharter: modelParams ≠ trusted; allowlist отклоняет `approved`/`confirmed`/`expected_sha256` по имени). Повторный propose при живом черновике показывает диалог снова (тот же хеш, пока draft не менялся).

## Решение 2: Фиксация-запуск как одна операция

Точка «фиксация» и точка «запуск» совмещены: после `true` выполняется последовательность (spec «Фиксация-запуск»): конфликты → запись wx-файла вне рабочего каталога → перечитывание и сверка хеша → пин корня → createChain → runtime+режим+кикофф. Порядок шагов выбран так, чтобы отказ после перехода в новый режим был невозможен: изменения runtime, включение режима и отправка кикоффа — последний шаг; отправка кикоффа — постановка сообщения в очередь (`sendWhenReady` — внутренний вызов, внешних зависимостей не имеет, отказать по внешней причине не может). Отказ при отказе шагов 4–5 удаляет всё, что создала операция: файл хартии (best-effort `rmSync`), каталог созданной кампании и каталог журнала цепочки (оба созданы только что); runtime не тронут (его меняем последним). Промежуточного «хартия зафиксирована, но цепочка не запущена» состояния не существует; повторный propose определён для двух случаев: живой черновик (диалог снова) и успешная фиксация (возврат записи первой фиксации, без диалога и без изменений состояния — приоритет над активной-цепочечным отказом, см. Решение 4). Запись о первой фиксации хранится в runtime (`{path, sha256, chainId}`).

Файл: `<workDir>/../charter-<rootId>-<yyyyMMdd-HHmmss>.json`, создание эксклюзивное (флаг `"wx"`; `writeFileAtomic` не даёт wx); коллизия → отказ `charter_path_taken`, существующий файл не трогаем. Целевой путь вычисляется до создания кампании (шаг 4), чтобы откат знал путь. realpath-проверка `charterInsideWorkdir` перед записью. Каноническая сериализация: `JSON.stringify(charter, null, 2) + "\n"` — ровно те байты, чей хеш показан.

## Решение 3: Генерация корня и связь с launch-веткой

Launch-ветка флагов (`/autoresearch research --charter ... --id ...`) остаётся без изменений: она требует `--id` (review B3) и работает с готовым файлом владельца. Charter-команда пиннит корень сама: id из `--id`, иначе `bench-<метка времени>` по правилам draft research-кампаний (тот же генератор с суффиксом на коллизию; коллизия с существующей кампанией на шаге createCampaign даст `campaign_exists` — отказ, полный откат, состояние чисто). После пина вызывается общий код запуска: `createChain` → `runtime.researchChain = { chainId, workDir, charterPath, charterSha256, charter }` → включение режима → бриф-кикофф. Практически launch-последовательность (journal, runtime, режим, кикофф) выносится во внутреннюю функцию, вызываемую из обоих входов; диалог `acceptLaunchCharter` в charter-пути не вызывается — его роль сыграл propose (доверенные байты = перечитанный файл, хеш сверен).

## Решение 4: Черновик, замена, конфликты

Черновик — поле runtime (`charterDraft`), не переживает перезапуск pi (заявленное остаточное: владелец начинает заново). Новый `draft` заменяет `charterDraft` целиком; повторный вызов `/autoresearch charter` при живом черновике (без активной цепочки/кампании) не отказывает — открывает диалог заново, новый draft заменит старый. Конфликт-проверка — общая функция `charterLaunchConflict(ctx)`: активная цепочка (`runtime.researchChain !== null`) или research-кампания (проверка из launch-ветки: `researchBlocksOrdinaryLoop`-эквивалент) — вызывается при входе в команду и ещё раз внутри propose перед записью (spec «Конфликт возник между фазами»). Инструмент: при активной цепочке отказывают `draft` и `propose` с живым черновиком — черновиком нельзя повлиять на запущенную цепочку; повторный propose без черновика возвращает запись первой фиксации (приоритетное правило, spec). Параллельные сессии pi: `charterDraft` и запись о фиксации — per-runtime, общих блокировок нет; две сессии могут создать две цепочки в одном рабочем каталоге — заявленный остаточный риск (как и параллельные сессии в остальном проекте).

## Решение 5: Дельта к замороженной спеке

Только ADD: новая способность `charter-launch` ссылается на требования research-charter («идёт по существующим требованиям»), тексты замороженных требований не меняются. Сценарий «Файл подменён после диалога до записи» из rev.1 удалён как нереализуемый (файл пишет сама система; граница подмены — запись→перечитывание, покрыто сценарием «Расхождение после записи»).

## Решение 6: stop_rules и не-пустые строки

`validateCharter` (уже реализовано) дополнительно требует непустых строк в `stop_rules` — это уже существующее поведение кода (charter.ts: «must be a non-empty string»), не новое правило спеки; charter-спека замороженной редакции этого не запрещает. Противоречия нет: замороженная спека задаёт тип, код ужесточает до непустых; в charter-launch это не дублируется — валидация одна, в `validateCharter`.
