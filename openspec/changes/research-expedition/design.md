# Design: research-expedition

## Контекст

Реализовано и работает (проверено по коду 2026-11-12):

- **Цепочка** (research-charter, rk6 ГОДЕН): `chain.json` — append-only журнал с хеш-цепочкой и внешним якорем `chain-head` (`chain-journal.ts`); `ChainEntry = {type: string, at, prev_hash, [key: string]: unknown}` — типы записей не ограничены enum'ом, `verifyChain` проверяет только хеш-цепочку и корень `chain_created`. Автоподтверждение дочерних брифов: каждый вопрос несёт `finding_refs` — пары `{campaign, question}`, указывающие на вопрос, закрытый **с доказательством** вердиктом, в **любой** кампании этой цепочки. Линейность: одна кампания за раз, не более одного потомка. Статусы цепочки: `active / awaiting_child / limit_reached / stopped_by_owner / stopped_by_rule / manual_check_required / completed`.
- **Стоп-самоотчёт**: `research chain_stop` с `rule_id` из `stop_rules` хартии — без диалога владельца; диалоговый путь — тот же вызов без `rule_id` (index.ts ~9624).
- **Guard запуска** (research-campaign-switch, 8a6cd6f): кампании активной цепочки не закрываются автозакрытием (`chainCampaignIds`); честные отчёты зависших кампаний; state-aware nudges.
- **Бриф-механика для образца** (в коде): `research_brief draft/propose` — draft валидирует и сохраняет, `propose` показывает владельцу диалог с SHA-256 (обёртка headless: `--approve-charter-sha`, код выхода 3 на отказ); `optimize_brief` — тот же двухфазный паттерн для обычного цикла.
- **TUI-поверхности** (в коде): `ctx.ui.setWidget("autoresearch", ...)` с `render(width)` — дашборд и tree-режим (`/autoresearch tree`); транскрипт-превью через `renderCall` (бриф рисуется в строке вызова инструмента); автокомплит — `AUTORESEARCH_SUBCOMMANDS` в `parallel/config-ui.ts` (там уже есть `research`).
- **Хартия — allowlist**: `max_campaigns`, `max_depth`, `stop_rules` — другие поля отклоняются. Расширять замороженную charter-спеку экспедиция не может и не должна — поэтому документ экспедиции **содержит** хартию как проверяемый подобъект (D1).
- **research-map** (rev.11, утверждён, НЕ реализован): direction review — документ с обязательными дисклеймерами; advisory-сигнал исчерпания всегда `unknown`, «не доказательство».

Щель: у цепочки нет артефакта «территории»; вход для владельца — ручной charter.json + два подтверждения; прогресс не виден в TUI.

После фазы 2 владелец свободен: после каждого отчёта кампании режим остаётся ON, механика charter отправляет ровно одно продолжение (`awaiting_child`), в которое вшивается срез карты (D6). Агент просыпается, видит карту, решает, едет дальше. Полный цикл итерации — §«Анатомия итерации».

## Goals / Non-Goals

**Goals**
- Порог входа: одна команда `/autoresearch expedition <цель>`, вопросы владельцу в чате, хартию пишет агент, подтверждение — ровно одно.
- Память о территории, переживающая компакцию и смену сессий: карта направлений в журнале цепочки.
- Аудируемость решений: каждое открытие/pivot/закрытие — запись с обоснованием и ссылками на находки.
- Механический предикат «нет открытых направлений» (territory_complete) для экспедиционных стоп-правил — значение true означает отсутствие открытых направлений, не полноту исследования.
- Видимость в TUI: виджет карты (векторы, вопросы, статусы) при активной экспедиции.
- Один итоговый документ экспедиции (карта + решения + отчёты кампаний).
- Минимальные дельты к существующим спекам: единственная — headless-launch (новые флаги того же контракта).

**Non-Goals**
- Ветвление (дерево направлений, параллельные кампании) — charter фиксирует «не более одного потомка»; отдельное будущее изменение.
- Экспедиция над осями метрик обычного цикла (analysis.jsonl, доверенные ступени S_exh) — v2, после реализации research-map.
- «Доказанное исчерпание» направления — в кампаний-субстрате недостижимо (D4).
- Реализация research-map (наблюдения, passports, analysis) — независимый change.
- Бюджеты по токенам/времени (решение владельца 2026-11-10: не вводить).
- Ранжирование направлений системой, автозапуск кампаний без промежуточного отчёта — выбор всегда за агентом (D6).

## Decisions

### D1. Точка входа — subcommand `/autoresearch expedition`; документ экспедиции содержит хартию как подобъект

**UX-контракт (решение владельца 2026-11-12):** владелец пишет `/autoresearch expedition Векторы`, агент задаёт вопросы обычным чатом, собирает документы, показывает одно подтверждение, запускает. Экспедиция — **явный вход**, не маркер: entry-point не подделать агентом, и это правильнее для инструмента, который по умолчанию едет автономно.

```
 ВЛАДЕЛЕЦ                         АГЕНТ                            СИСТЕМА (механика)
    │                                │                                   │
    │ /autoresearch expedition       │                                   │
    │   Векторы                      │                                   │
    ├───────────────────────────────►│                                   │
    │                                │ читает цель, docs, git-историю    │
    │◄── "Что считаем векторами?" ───┤  РАЗВЕДКА ЦЕЛИ — обычный чат:     │
    │─── "regex-метрики, sync, ..."─►│  территория, критерии             │
    │◄── "лимиты по времени?" ───────┤  "что считаем      │
    │─── "не больше 10 кампаний" ───►│   завершением?",   │
    │                                │   ограничения      │
    │                                │  когда всё ясно:                  │
    │                                │ expedition_brief draft ──────────►│ валидация:
    │                                │  ┌─────────────────────┐          │  charter-подобъект
    │                                │  │ charter:            │          │  против allowlist,
    │                                │  │  stop_rules:        │          │  цель/векторы/бриф
    │                                │  │   territory_complete│          │  против схем
    │                                │  │  max_campaigns: 10  │          │
    │                                │  │ goal: "Векторы..."  │          │
    │                                │  │ directions: D1..D3  │          │
    │                                │  │ campaign0: {brief}  │          │
    │                                │  └─────────────────────┘          │
    │   expedition_brief propose     │                                   │
    │◄── ДИАЛОГ ─────────────────────┤                                   │
    │  ┌──────────────────────────┐  │                                   │
    │  │ Expedition SHA-256: 9f2a │  │                                   │
    │  │ Goal: ...                │  │                                   │
    │  │ D1 regex … D2 sync … D3… │  │                                   │
    │  │ Q1..Q3 (кампания №0)     │  │                                   │
    │  │ stop: territory_complete │  │                                   │
    │  │ [Y] Start / [N] Cancel   │  │                                   │
    │  └──────────────────────────┘  │                                   │
    │── [Y] ────────────────────────►│                        chain.json создан,
    │                                │                        D1..D3 → direction_opened,
    │                                │                        c0 → campaign_added,
    │                                │                        Research mode ON
```

**Разделение ролей:** агент **формирует** документ, владелец **утверждает** его хешем (один диалог, механизм как у `research_brief propose` / `optimize_brief propose`). Агент физически не может начать экспедицию без [Y].

**Документ экспедиции — один файл**, чей `charter`-подобъект — обычный allowlist-объект (`stop_rules`, опционально `max_campaigns`/`max_depth`), проверяемый теми же правилами состава, что charter-файл сегодня. Цель, стартовые направления и бриф кампании №0 живут рядом в том же документе. Таким образом замороженная charter-спека не получает дельты: хартия как таковая не изменилась — изменилось, кто её написал и как она доставлена (внутри документа экспедиции, утверждённого одним хешем).

**Хранение:** внутренние черновики до подтверждения живут в `<state-root>/research-expedition-drafts/` (внутренний артефакт); на propose документ MUST оказаться в файле **вне рабочей директории** (правило charter «charter вне workdir» переносится на подтверждаемый документ — realpath-проверка та же): propose принимает путь вне workdir или без пути переносит последний draft в файл вне workdir; в диалоге предложения печатается путь.

**Реализация входа:** ветка `expedition` в handler'е `/autoresearch` (рядом с `research`), запись в `AUTORESEARCH_SUBCOMMANDS` для автокомплита. Ветка включает research-режим и фазу проектирования (брифинг-поверхность `expedition_brief`).

**Детали журнала при создании:** записи пишутся в порядке `chain_created` (общий корень механики цепочки — `verifyChain` сверяет именно его; payload экспедиции в корень не пишется) → `expedition_created` (цель, SHA-256 документа — признак экспедиционности для инструментов карты) → `direction_opened` × N → `campaign_added` №0 (бриф №0 из документа; подтверждён самим подтверждением документа, без отдельного диалога); далее запускается кампания №0. Механический вызов на существующем коде: сегодня `createChain` не принимает экспедиционную нагрузку в корень — `expedition_created` решает это отдельной записью сразу после корня; сегодня `chain_stop` принимает любой валидный `rule_id` — для `territory_complete` в экспедиционной цепочке предикат вычисляется ДО смены статуса, отказ не меняет состояние.

**Механика принятия документа (adapter):** документ экспедиции принимается собственным валидатором (правила состава хартии применяются к подобъекту `charter`, остальные поля — по схеме документа) и собственным путём подтверждения с трёхсторонней сверкой хеша (по образцу `acceptCharter`: диалоговый SHA / операторский SHA / файловый SHA в момент ответа) — НЕ через `acceptCharter` (тот валидирует файл строго как хартию и отверг бы документ с extra-полями). Цепочка создаётся общим механическим путём с хартией, извлечённой из `charter`-подобъекта — только это через существующий код.

**Отклонённая альтернатива (предыдущая редакция):** маркер в журнале (`direction_opened` делает цепочку экспедиционной) без отдельной команды. Причина отклонения: владельцем выбран явный вход; маркер-подход оставлял ручное написание charter.json и два подтверждения.

### D2. Карта живёт в chain.json: типы записей и их схема

Экспедиционные записи — обычные записи журнала с `type` из фиксированного набора:

```jsonc
// порядок при создании: chain_created (общий корень механики) → expedition_created →
// direction_opened × N → campaign_added (бриф №0)
{type:"expedition_created", goal:"Векторы…", doc_sha256:"9f2a…"}               // признак экспедиционности; хеш документа экспедиции
{type:"direction_opened",    dir:"D2", why:"F3: appendFile синхронный (c1-c1/Q2)",
                             refs:[{campaign:"c1-c1",question:"Q2"}]}          // refs опциональны для стартовых направлений
{type:"direction_activated", dir:"D2", campaign:"c1-c2"}                       // бриф кампании ссылается на вопросы D2
{type:"direction_resolved",  dir:"D2", refs:[{campaign:"c1-c2",question:"Q1"}]}
{type:"direction_rejected",  dir:"D2", refs:[{campaign:"c1-c2",question:"Q1"}]}
{type:"direction_parked",    dir:"D3", reason:"ниже ожидаемого выигрыша, вернёмся при pivot"}
{type:"direction_reopened",  dir:"D3", reason:"review-002 предложил вернуться"}
{type:"direction_advisory",  dir:"D4", review_ref:".auto/reviews/direction-<ts>.md",
                             review_sha256:"…",
                             note:"advisory: идей нет; исчерпание НЕ доказано"}
{type:"pivot",               from:"D2", to:"D5", reason:"...", refs:[...]}     // to: существующий open/parked или новый dir
{type:"expedition_stop",     rule:"territory_complete", basis:"predicate|owner"}
```

Правила записи:
- **append-only как весь журнал**: направление никогда не «меняет статус» — новый факт добавляется новой записью; состояние = replay (последнее событие по dir + валидность переходов).
- **каждая запись несёт обоснование** (`why`/`reason`/`note` + `refs` где применимо) — аудируемость решений это контракт, не пожелание.
- **переходы валидируются при записи** (fail-closed): `resolved`/`rejected` требуют `refs`, каждая пара которых проходит ту же механическую проверку, что автоподтверждение брифов (вопрос закрыт с доказательством в кампании этой цепочки); `direction_advisory` требует существующего `review_ref` с sha256; `activated` требует кампании этой цепочки в фазе research. Невалидный переход — отказ записи, журнал не меняется.
- **одна активная кампания = один `active` dir**: `direction_activated` для нового dir без закрытия предыдущего активного отказывает (pivot — атомарная замена). Статус dir'а, чья кампания остановлена без закрытия (campaign-switch: abandon), не меняется — расхождение «dir active, кампания stopped» является видимым неполным состоянием и попадает в отчёт экспедиции как «незакрытая ветка» (честно, не подчищается).

### D3. Машина состояний направления

```
                    direction_opened + обоснование
                            │
                            ▼
                        ┌───────┐   activate    ┌────────┐
                        │ OPEN  │──────────────►│ ACTIVE │◄──── одно
                        └───┬───┘               └───┬────┘     одновременно
                            │                       │
        reopen (данные      │            ┌──────────┼──────────────┬───────────┐
        появились позже)    │            │resolve   │reject        │advisory   │park
                            ▼            ▼          ▼              ▼           ▼
                        ┌────────┐  ┌──────────┐ ┌──────────┐ ┌───────────┐ ┌────────┐
                        │ PARKED │  │ RESOLVED │ │ REJECTED │ │ ADVISORY_ │ │ PARKED │
                        └────────┘  └──────────┘ └──────────┘ │ EXHAUSTED │ └────────┘
                            ▲            ▲          ▲         └───────────┘
                            │            │          │         честная метка:
                            └────────────┼──────────┘         "идей нет,
                                     reopen                исчерпание НЕ доказано"

 ЧТО ТРЕБУЕТ МЕХАНИКА (без этого refusal):
   RESOLVED  → finding_refs с проверенными находками цепочки (механическая проверка)
   REJECTED  → тоже находки: «не туда» должно быть обосновано данными
   ADVISORY  → review_ref: документ-разбор с sha256
   PARKED    → обоснование (свободный текст)
   pivot     → = закрыть ACTIVE + открыть/активировать другой, одним событием
```

### D4. Статусы и уровни доказанности: «доказанно исчерпано» не существует

Ключевая честная граница: **«доказанно исчерпано» в v1 не существует**. `resolved`/`rejected` механически доказывают только «вопрос по этому направлению закрыт вердиктом с доказательством» — не полноту исследования направления. `advisory_exhausted` — самоотчёт агента, опирающийся на direction review (документ по research-map с обязательными дисклеймерами); он всегда записывается с пометкой недоказанности и в отчёте экспедиции печатается отдельной строкой с «основание не является доказательством». Это ровно принятый владельцем в charter остаточный риск («находки порождает сам агент»), поднятый на уровень карты.

Механическая защита от дешёвого закрытия: `resolved`/`rejected` требуют `refs` на конкретные закрытые с доказательством вопросы — «закрыть направление без единого вердикта» невозможно; «закрыть одним мелким вердиктом» возможно (остаточный риск, виден в отчёте: сколько вопросов кампаний dir'а пришлось на вердикт).

### D5. Стоп-правило `territory_complete`: механический предикат

В `stop_rules` хартии (массив строк) экспедиция резервирует **имя правила** `territory_complete`. Семантика задаётся не текстом «when», а вычислимым предикатом:

- **territory_complete = true** ⇔ в карте нет ни одного dir в статусе `open`/`active`, И не было `pivot` после последнего закрытия направления (нет «хвоста выбора»), И суммарно открытых направлений ≥ 1.

Вычисление — чистая функция от журнала (replay), выполняется в двух местах:
1. **при самоотчёте агента** (`chain_stop` с `rule_id: "territory_complete"`): система вычисляет предикат ДО любого изменения статуса цепочки; при `true` — штатная остановка `stopped_by_rule` (как сегодня); при `false` — отказ с перечнем живых направлений, состояние не меняется. Формулировка «территория пройдена» нигде не используется как утверждение успеха: пользовательские тексты говорят «предикат выполнен» с перечнем незакрытых направлений (parked, advisory);
2. **в отчёте экспедиции** — значение предиката и состав (какие dir'ы чем закрылись) печатаются явно.

Владелец (`chain_stop` без rule_id, диалог) может остановить экспедицию при любом значении предиката — как и сегодня. Прочие стоп-правила хартии (свободные имена) ведут себя по-старому: самоотчёт. Никаких тайминговых эвристик («не трогали N кампаний → всё исследовано») — только явные события карты (принцип campaign-switch).

### D6. Главный цикл: анатомия итерации — агент решает, система фиксирует и проверяет

```
┌─────────────────── ИТЕРАЦИЯ N (автоматическая) ───────────────────────────┐
│                                                                            │
│ ▸ ТРИГГЕР: отчёт кампании N-1 записан, режим ON, механика charter          │
│   отправила continuation с {срез карты + сводка отчёта + находки}          │
│                                                                            │
│ [1] РЕШЕНИЕ АГЕНТА: куда ехать? (см. ниже — «Как агент выбирает вектор»)   │
│                                                                            │
│ [2] ФИКСАЦИЯ РЕШЕНИЯ                                                       │
│     research expedition activate Dk        (или pivot / park / reopen)     │
│     + обязательное обоснование ("D1 дал f3: regex O(n²) — копаю глубже")   │
│     СИСТЕМА: проверяет легальность перехода (D3), пишет событие в журнал.  │
│     Нелегально → refusal; агент передумывает.                              │
│                                                                            │
│ [3] БРИФ ЭТАПА (кампании N)                                                │
│     research_brief draft: 1–4 вопроса ЭТОГО этапа                          │
│     каждый вопрос → finding_refs: [f3] — «я это спрашиваю, потому что      │
│     находка f3 из кампании c1 показала X» (charter-механика, как есть)     │
│                                                                            │
│ [4] АВТОПОДТВЕРЖДЕНИЕ (charter, как есть)                                  │
│     каждый вопрос ссылается на находку цепочки?                            │
│       да  → brief approved БЕЗ ДИАЛОГА; записывается direction_activated   │
│       нет → refusal; агент переделывает бриф                               │
│                                                                            │
│ [5] КАМПАНИЯ N — РАБОТА                                                    │
│     research open Q1 → агент РЕАЛЬНО работает (тесты, замеры, код)         │
│     research record Q1 evidence_ref=path:строки (доказательство + хеш)     │
│     research close Q1 verdict=confirmed rule=Q1-yes (по decision rule)     │
│     … пока все вопросы этапа не закрыты …                                  │
│                                                                            │
│ [6] ОТЧЁТ КАМПАНИИ                                                         │
│     research report → report.md + находки в findings ledger                │
│     СИСТЕМА: chain status → awaiting_child, ровно одно продолжение → [1]   │
│                                                                            │
│ [7] РЕШЕНИЕ АГЕНТА: что с вектором Dk?                                     │
│     resolved / rejected / advisory / parked / продолжить                   │
│                                                                            │
│ [8] СТОП-ПРОВЕРКА                                                          │
│     все векторы закрыты? → research chain_stop rule_id=territory_complete  │
│     СИСТЕМА: механический предикат (D5)                                    │
│       прошёл   → ФАЗА 4: отчёт экспедиции, режим OFF                       │
│       не прошёл → refusal с перечнем живых направлений → агент к [1]       │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

**Как агент выбирает вектор (шаг [1]).** В `awaiting_child` агент видит четыре источника: срез карты (статусы + обоснования), последний отчёт (открытые вопросы, вердикты), находки цепочки (findings ledger), цель из документа экспедиции. Выбор — суждение агента; система не ранжирует и не выбирает:

```
        Текущий ACTIVE вектор: последний этап дал находки, тема не раскрыта?
             │да                          │нет
             ▼                            ▼
   Следующая кампания по НЕМУ    Вектор кончился идеями?
   (глубже в тот же Dk)              │да                │нет
             │                       ▼                  ▼
             │              expedition advisory  Есть вектор ценнее
             │              (честно: «идей нет,  для ЦЕЛИ?
             │               исчерпание не        │да            │нет
             │               доказано»)           ▼              ▼
             │                          pivot: закрыть    PARKED Dk
             ▼                          ACTIVE + открыть  («мало данных,
        бриф этапа [3]                  новый Dk+1         вернусь позже»)
                                                   → activate другой Dk
```

Ограничение механики: **один ACTIVE одновременно**; другой вектор — сначала закрыть текущий (`resolve`/`reject`/`advisory`/`park`) или `pivot` (атомарно: закрыл + открыл + обосновал).

Пример реальной цепочки решений (cache-экспедиция):

```
iteration 1: активирован D1 «метрики»    → c1 → находки f1 (regex O(n²)), f2
iteration 2: D1 не раскрыт, продолжаю    → c2 → f3 (кэш решает, но не всё)
iteration 3: D1: «кэш+ленивый парсинг закрывают вопрос» → RESOLVED [f2,f3]
iteration 4: карта: D2 «append-sync» ценнее D3 → pivot → activate D2
iteration 5: c3: синхронизация не виновата → REJECTED D2 (данные есть)
iteration 6: D3 «локи» — идей нет после 2 этапов → ADVISORY («не исчерпано —
             неизвестно», честная метка)
iteration 7: карта пуста, все закрыты → chain_stop territory_complete →
             предикат прошёл → ФИНАЛ
```

**Что система НЕ делает:** не выбирает за агента, не ранжирует dir'ы, не автозапускает кампании без промежуточного отчёта (триггер итерации — всегда отчёт). Решения с обоснованиями — работа агента; карта делает их видимыми и проверяемыми.

**Сбои не ломают цикл:** упавшая кампания получает честный отчёт (campaign-switch), вектор остаётся ACTIVE — агент на следующей итерации решает: повторить, закрыть вердиктами из частичного журнала кампании (журнал сохранён) или park'нуть. Нечитаемое состояние → `manual_check_required` → экспедиция останавливается и зовёт владельца (fail-closed, никаких тихих пропусков).

### D7. TUI-виджет карты: обязательная поверхность

При активной экспедиции виджет `autoresearch` (тот же `ctx.ui.setWidget`, что у дашборда) рендерит карту вместо обычного дашборда:

```
┌──────────────────────────────────────────────────────────┐
│ 🧭 expedition │ Векторы │ c3 running                      │
├──────────────────────────────────────────────────────────┤
│ ✅ D1 metrics        resolved │ c0,c1,c2                  │
│ 🔄 D2 append-sync    ACTIVE   │ c3: Q1 open, Q2 open      │
│ 💤 D3 lock-races     parked   │ «мало данных»             │
│ ○  D4 …              open     │                           │
├──────────────────────────────────────────────────────────┤
│ territory: 1/3 │ campaigns 3/10 │ next: awaiting_child   │
└──────────────────────────────────────────────────────────┘
```

- **заголовок**: цель (усечённая), текущая кампания (`cN running` / `awaiting_child` / `stopped_by_rule`…);
- **строки направлений**: глиф статуса (✅ resolved / 🔄 active / 💤 parked / ○ open / ❓ advisory / ❌ rejected), имя, статус, активная кампания с её открытыми вопросами или обоснование закрытия/парковки; ширина обрезается как в дашборде (`truncateToWidth`);
- **футер**: `territory X/Y` (закрыто/всего), `campaigns N/лимит` (или N), следующий шаг цепочки.

Механика рендера: виджет — функция от файлов (replay журнала + журнал активной кампании), перерисовка по `requestRender` как у дашборда; при отсутствии UI (`hasUI = false`) виджета нет — видимость дают обёртка headless (вывод статуса) и отчёт экспедиции. Узкие экраны: <N столбцов — двухколоночная компоновка сжимается в `dir │ status │ причина` (как дашборд выбирает 4/6 строк по ширине).

Дополнительные поверхности (не обязательные, по месту при спецификации): полный просмотр карты — действие `research expedition status` (текстовая таблица в чат); транскрипт-превью `expedition_brief propose` — по образцу `renderCall` у `research_brief` (документ рисуется в строке вызова до диалога).

### D8. Отчёт экспедиции

Собирается машинно (по образцу честного отчёта research-campaign-switch) при любом финальном статусе цепочки (`completed`, `stopped_by_*`, `limit_reached`) как **дополнительный файл** в каталоге цепочки (`expedition-report.md`) и печатается в ответе финального отчёта:

```markdown
# Expedition report: <chain-id>
Status: <final chain status> | Stop: territory_complete (predicate, computed <ts>) | Campaigns: N
Goal: <why из документа экспедиции>

## Map (final)
| Dir | Status | Basis | Evidence |
| D1  | resolved | verdict confirmed | c1-c1/Q1 (finding) |
| D2  | rejected | verdict rejected  | c1-c3/Q1 |
| D4  | advisory_exhausted | UNKNOWN basis: self-report + review | .auto/reviews/direction-...md |
| D3  | parked | agent decision | reason: «вернёмся при pivot» |

## Timeline (decisions)
direction_opened D1..D4 → activated D1 → resolved D1 → pivot D2 → … → expedition_stop

## Unfinished
D4: advisory self-report is NOT proof of exhaustion.
D3: parked, never resolved.
```

Формулировки: незакрытые dir'ы — «не исследовано», advisory — с явным «не доказательство»; никакой агрегированной статистики «покрыто 80% территории» (нет метрики площади). Файл — дополнение, не замена: отчёты кампаний остаются на месте, кампании цепочки не архивируются.

### D9. Интерфейсные поверхности: сводка

| Поверхность | Механизм | Статус в спеке |
|---|---|---|
| `/autoresearch expedition <цель>` | ветка в handler'е + `AUTORESEARCH_SUBCOMMANDS` | обязательна |
| фаза проектирования (вопросы владельцу) | обычный чат, без нового инструмента | обязательна (сценарий) |
| `expedition_brief draft/propose` | новый инструмент по образцу research_brief (диалог + SHA) | обязательна |
| `research expedition <subaction>` | действие инструмента `research` (open/activate/resolve/reject/advisory/park/reopen/pivot/status/stop) | обязательна |
| срез карты в `awaiting_child`-продолжении | интерполяция в существующее продолжение | обязательна |
| предикат на пути `chain_stop` | проверка rule_id=territory_complete | обязательна |
| виджет карты | ветка рендера `setWidget("autoresearch")` | обязательна (D7) |
| транскрипт-превью документа | `renderCall` по образцу research_brief | опциональна |
| headless `--expedition-doc` + `--approve-expedition-sha` | флаги обёртки, контракт headless-launch | обязательна (единственная дельта к спекам) |

Действия карты требуют активной экспедиционной цепочки сессии (запись `expedition_created` в журнале) и проходят через `appendEntry` (lock + verify → fail-closed на повреждение, `manual_check_required`).

### D10. Не входит (повторно, из proposal)

Ветвление; оси метрик; доверенные ступени S_exh; реализация research-map; бюджеты; параллелизм; миграции (старые chain.json без экспедиционных записей — обычные цепочки; `/autoresearch expedition` при живой не-экспедиционной research-кампании ведёт себя как обычный запуск: guard campaign-switch срабатывает как есть).

## Risks

- **Карта как самоотчёт**: статусы dir'ов записывает агент; механика доказывает существование находок, не полноту территории. Смягчение: refs-проверки, обязательные обоснования, advisory виден как unknown в отчёте и виджете (принятый residual risk charter, задокументирован).
- **Хартия, написанная агентом**: агент формирует рамки своей же автономии. Смягчение: документ утверждается владельцем одним хешем (он видит стоп-правила и лимиты в диалоге), состав charter-подобъекта проверяется allowlist-механикой, владелец может остановить в любой момент (`stopped_by_owner`).
- **Состояние = replay растущего журнала**: цепочка на десятки кампаний делает replay на каждое действие/рендер O(N). Для v1 (десятки записей) приемлемо; виджет рендерит по requestRender, не по таймеру. Оптимизация (снимок состояния) — вне скоупа.
- **Parked навсегда**: parked не блокирует `territory_complete` (иначе экспедиция не кончится) — осознанно; «прикрыли глаз» виден в отчёте (Unfinished) и виджете (💤).
- **Расхождение «active dir без живой кампании»** (abandon по campaign-switch): не подчищается, показывается как незакрытая ветка (отчёт Unfinished; виджет — ACTIVE без running-кампании). Смягчение: state-aware nudges уже подталкивают к stop+report.
- **Зарезервированное имя правила**: юзер-хартия со случайным правилом «territory_complete» в **не-экспедиционной** цепочке (созданной по --charter без документа экспедиции) останавливается по-старому (самоотчёт без предиката) — обратно совместимо. Проверка предиката включается только для экспедиционных цепочек (созданных через документ экспедиции).
- **Фаза проектирования может затянуть чат**: агент обязан спросить только то, чего не хватает для документа (цель/критерии/ограничения/стартовые векторы); сценарий спеки фиксирует: вопросы пакетом, не по одному; «всё ясно» — когда документ можно собрать без домыслов.

## Тестовая стратегия (проверяемость сценариев)

- **Вход и фаза проектирования**: subcommand зарегистрирован (автокомплит, help); без UI-диалога propose отказывает честно; отказ владельца [N] не создаёт журнал; подтверждаемый документ вне workdir (realpath-отказ для пути внутри); draft в каталоге черновиков `<state-root>/research-expedition-drafts/`, resume находит последний детерминированно.
- **Документ экспедиции**: charter-подобъект против allowlist (чужое поле → отказ); бrief №0 валиден; стартовые направления ≥1; повторный propose при изменённом документе → новый SHA.
- **Валидность переходов**: resolved/rejected без refs → отказ; refs на незакрытый/чужой-цепочки вопрос → отказ; advisory без review_ref → отказ; активация при живом другом active → отказ; pivot атомарен; повреждение журнала → manual_check_required (существующее поведение, фиксируется).
- **Replay-детерминизм**: повторное чтение журнала даёт ту же карту; порядок записей значим (последнее событие по dir выигрывает).
- **territory_complete**: открытый dir → false (chain_stop отказывает с перечнем); все закрыты → true (остановка работает); parked не блокирует; пустая карта → отказ (не экспедиция); не-экспедиционная цепочка с rule_id «territory_complete» останавливается по-старому.
- **Виджет**: карта рендерится при активной экспедиции (строки/глифы/футер по фикстуре журнала); обычный дашборд не изменён (регресс); узкая ширина — обрезка без мусора; headless (без UI) — без ошибок.
- **Отчёт**: advisory печатается с «не доказательство»; parked в Unfinished; расхождение active-dir/остановленная кампания — в Unfinished; значение предиката в отчёте.
- **Продолжение к брифу**: срез карты присутствует в awaiting_child-продолжении экспедиционной цепочки, отсутствует в обычной.
- **Регресс**: все существующие charter-, campaign-switch- и launch-тесты зелёные; guard не закрывает кампании экспедиционной цепочки (chainCampaignIds).
- **Headless**: `--expedition-doc` + `--approve-expedition-sha` запускает экспедицию без диалога; неверный SHA → код 3; пауза awaiting_child → код 0 (существующий контракт).
