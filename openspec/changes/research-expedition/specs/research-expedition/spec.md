# Spec Delta: research-expedition

## ADDED Requirements

### Requirement: Точка входа expedition

Subcommand `/autoresearch expedition` SHALL быть зарегистрирован в списке подкоманд (автокомплит и справка) рядом с `research`. Вызов SHALL включать режим исследования и фазу проектирования, не создавая никакого состояния цепочки: состояние создаётся только после подтверждения документа экспедиции. При активной research-кампании вне цепочек MUST применяться guard запуска как при обычном запуске research (закрываемые закрываются, незакрываемые отказывают); при активной экспедиционной цепочке вызов MUST отказывать с указанием возобновить или завершить существующую экспедицию. При `ctx.hasUI = false` интерактивный запуск MUST отказывать с указанием на headless-обёртку.

#### Scenario: Команда запускает фазу проектирования
- **WHEN** владелец вызывает `/autoresearch expedition <цель>` при отсутствии активных кампаний
- **THEN** режим исследования включён, агент переходит к вопросам проектирования; каталог цепочки, журнал и брифы не созданы

#### Scenario: Активная research-кампания при запуске экспедиции
- **WHEN** экспедиция запускается при живой research-кампании вне цепочек
- **THEN** применяется guard запуска как при обычном запуске (закрываемые закрываются, незакрываемые — отказ с перечнем причин)

#### Scenario: Активная экспедиционная цепочка при повторном запуске
- **WHEN** `/autoresearch expedition` вызван при активной экспедиционной цепочке (`active` или `awaiting_child`)
- **THEN** отказ с указанием возобновить или завершить существующую экспедицию; журнал цепочки байт-в-байт не меняется; кампании цепочки не закрываются guard'ом

#### Scenario: Нет UI
- **WHEN** команда вызвана в сессии без TUI
- **THEN** отказ с указанием headless-пути; состояние не создано

### Requirement: Фаза проектирования и документ экспедиции

Фаза проектирования SHALL идти в обычном чате: агент задаёт владельцу только недостающие для документа вопросы (территория, критерии пройденности, ограничения, стартовые направления) — пакетом, без пошаговых подтверждений. Инструмент `expedition_brief` (draft) SHALL собирать документ экспедиции — JSON: `charter` (объект, проходящий правила состава хартии), `goal`, `directions` (непустой массив; у каждого имя и обоснование), `campaign0` (бриф, проходящий стандартную схему). Подтверждаемый документ MUST находиться вне рабочей директории агента (realpath-проверка, по образцу charter): внутренние черновики до подтверждения живут в `<state-root>/research-expedition-drafts/` (внутренний артефакт, требованию «вне workdir» не подлежит), а propose принимает либо путь к файлу вне workdir, либо без пути переносит последний draft из каталога черновиков в файл вне workdir и предлагает его. Невалидный документ MUST отказывать с именованной причиной до диалога подтверждения. Документ SHALL приниматься собственным валидатором состава (не charter-валидатором): правила состава хартии применяются к подобъекту `charter`, остальные поля валидируются по схеме документа; и собственным путем подтверждения (requirement «Подтверждение документа экспедиции»), не через acceptCharter. Подтверждённый документ создаёт цепочку через общий механический путь создания с хартией, извлечённой из `charter`-подобъекта.

#### Scenario: Вопросы пакетом
- **WHEN** для документа не хватает данных
- **THEN** агент спрашивает недостающее одним сообщением; когда всё ясно — сразу собирает draft без промежуточных согласований

#### Scenario: Документ собран
- **WHEN** draft с корректными `charter`, `goal`, непустыми `directions` и валидным `campaign0`, сохранён в каталоге черновиков
- **THEN** документ сохранён, доступен `propose`

#### Scenario: Некорректный документ
- **WHEN** `charter` содержит поле вне allowlist, или `directions` пуст, или `campaign0` не проходит схему брифа
- **THEN** отказ с именованной причиной; диалог подтверждения не запрашивается

#### Scenario: Путь внутри рабочей директории
- **WHEN** для propose указан файл документа внутри рабочей директории (включая пути через симлинки)
- **THEN** отказ; документ не подтверждается

#### Scenario: Сессия потеряна после draft
- **WHEN** draft сохранён во внутреннем каталоге черновиков, подтверждение не состоялось, сессия завершена; владелец запускает `/autoresearch expedition` снова
- **THEN** последний неподтверждённый draft обнаружен детерминированно (каталог `<state-root>/research-expedition-drafts/`, не более одного неподтверждённого документа); для propose он переносится в файл вне рабочей директории, путь сообщается агенту и владельцу; состояние цепочки по-прежнему не создано

#### Scenario: Возобновление экспедиционной паузы
- **WHEN** экспедиционная цепочка в статусе `awaiting_child` и владелец хочет продолжить
- **THEN** продолжение — то же, что для обычных цепочек (`/autoresearch research --id <кампания>` указывает кампанию цепочки); отказ повторного `/autoresearch expedition` содержит этот путь возобновления

### Requirement: Подтверждение документа экспедиции

Диалог `expedition_brief propose` MUST начинаться строкой `Expedition SHA-256: <hex>` и приниматься только как строго `true`; он SHALL показывать цель, направления, вопросы кампании №0, стоп-правила и лимиты. Одно подтверждение фиксирует хартию, направления и бриф №0: отдельный диалог `Charter SHA-256` и подтверждение брифа №0 при создании экспедиции не запрашиваются (специальный случай общего правила подтверждения хартии — для цепочек, созданных из документа экспедиции). Модель MUST NOT передавать подтверждение, ожидаемый хеш или поля одобрения; вызов с неизвестными действию полями MUST отклоняться. Система MUST пере-вычислить хеш файла в момент подтверждения и MUST NOT фиксировать подтверждение, если файл изменился после показа. Отказ владельца оставляет систему без состояния цепочки. При `ctx.hasUI = false` подтверждение отклоняется.

#### Scenario: Владелец подтвердил
- **WHEN** диалог вернул строго `true` и файл не менялся с момента показа
- **THEN** документ зафиксирован с этим SHA-256: хартия, направления и бриф №0 подтверждены одним подтверждением; экспедиция создаётся без отдельных диалогов `Charter SHA-256` и `Brief SHA-256`

#### Scenario: Владелец отказал
- **WHEN** диалог вернул не `true`
- **THEN** документ не зафиксирован, состояние цепочки не создано

#### Scenario: Файл изменён при висящем диалоге
- **WHEN** файл документа изменён после показа, до ответа
- **THEN** подтверждение не фиксируется; состояние не создано

#### Scenario: Модель передаёт одобрение
- **WHEN** в вызове инструмента присутствуют `approved`, `confirmed`, `expedition_sha256`, `operator_confirmation` или поле вне allowlist действия
- **THEN** вызов отклоняется, документ не фиксируется

### Requirement: Создание экспедиции и хеш документа

При подтверждённом документе система SHALL создать журнал цепочки: корневая запись `chain_created` (общая механика цепочек, без экспедиционной нагрузки), сразу за ней `expedition_created` (цель, SHA-256 документа), затем `direction_opened` по каждому направлению документа (с его обоснованием), затем `campaign_added` корневой кампании (бриф №0 из документа), и запустить кампанию №0. Подтверждение документа подтверждает и бриф №0: отдельный диалог или хеш-подтверждение брифа №0 не запрашивается. Идентификаторы кампаний назначает система. SHA-256 подтверждённого документа SHALL далее сверяться как хеш хартии: изменение файла документа останавливает цепочку правилом «файл хартии изменился».

#### Scenario: Экспедиция создана
- **WHEN** документ подтверждён
- **THEN** журнал содержит `chain_created`, `expedition_created`, `direction_opened` × N (стартовые направления с обоснованиями), `campaign_added` кампании №0; кампания №0 стартует; отдельного подтверждения брифа №0 не было

#### Scenario: Документ изменён после создания
- **WHEN** файл документа изменён после подтверждения
- **THEN** цепочка останавливается по правилу «файл хартии изменился» (как изменение хартии)

### Requirement: Карта направлений

Карта направлений SHALL быть состоянием, вычисляемым детерминированным replay журнала цепочки: последнее событие по направлению определяет его статус. События карты: `expedition_created` (запись при создании после корневой `chain_created`; признак экспедиционности цепочки), `direction_opened`, `direction_activated`, `direction_resolved`, `direction_rejected`, `direction_parked`, `direction_reopened`, `direction_advisory`, `pivot`, `expedition_stop` (последний записывается системой при финальном статусе цепочки с основанием `owner` или `rule`). Каждое событие карты, кроме `expedition_created`, MUST нести обоснование (`why`/`reason`/`note`). Журнал append-only: события не переписываются и не удаляются. Действия карты на цепочке без записи `expedition_created` MUST отказывать (`not_an_expedition`); повреждение журнала отказывает все действия карты и цепочки (`manual_check_required`).

#### Scenario: Replay-детерминизм
- **WHEN** журнал прочитан повторно, в том числе новой сессией
- **THEN** карта идентична: статусы определяются последним событием по направлению

#### Scenario: Не-экспедиционная цепочка
- **WHEN** действие карты вызвано на цепочке без записи `expedition_created`
- **THEN** отказ `not_an_expedition`; поведение цепочки не меняется

#### Scenario: Повреждение журнала
- **WHEN** цепочка или журнал не проходят сверку головного хеша
- **THEN** действия карты и цепочки отказывают; статус `manual_check_required`

### Requirement: Переходы статусов направлений

Переходы SHALL валидироваться при записи (fail-closed; невалидный переход отказывает без записи в журнал). `resolved`/`rejected` требуют непустой `refs`, где каждая пара `{campaign, question}` указывает на вопрос, закрытый с доказательством вердиктом в кампании этой цепочки (та же механическая проверка, что автоподтверждение брифов). `advisory` требует существующий `review_ref` с записанным sha256 файла обзора. `park` и `reopen` требуют причину. `activated` требует кампанию этой цепочки в фазе research; активных направлений не более одного. `pivot` — атомарная замена: одна запись закрывает текущее активное направление и открывает/активирует целевое. Допустимые переходы: `open→active`, `open→parked`, `active→resolved|rejected|advisory|parked`, `parked|advisory|resolved|rejected→open` (reopen).

#### Scenario: Закрытие без находок
- **WHEN** `resolve`/`reject` с пустым `refs` или парой на незакрытый вопрос, чужую кампанию или кампанию вне цепочки
- **THEN** отказ с именованной причиной; журнал не меняется

#### Scenario: Второй активный
- **WHEN** `activate` направления, пока другое `active` (вне `pivot`)
- **THEN** отказ; предыдущее направление должно быть закрыто, припарковано или заменено через `pivot`

#### Scenario: Advisory без документа
- **WHEN** `advisory` с несуществующим `review_ref` или без sha256
- **THEN** отказ; advisory возможен только с опорой на записанный обзор

#### Scenario: Pivot атомарен
- **WHEN** `pivot` с валидными `from` (активное направление), `to` (новое или `open`/`parked`) и обоснованием
- **THEN** одна запись журнала; полузакрытых состояний не возникает; при невалидности любого элемента запись отказывает целиком

#### Scenario: Reopen возвращает в open
- **WHEN** `reopen` припаркованного, advisory, resolved или rejected направления с причиной
- **THEN** направление снова `open`; активация требует отдельного `activate` или `pivot`

### Requirement: Уровни доказанности статусов

Система SHALL различать механически обоснованные статусы (`resolved`, `rejected` — вердикты с доказательством по `refs`) и `advisory_exhausted` (самоотчёт агента с опорой на обзор). Статуса «доказанно исчерпано» в v1 не существует: система MUST NOT представлять `advisory_exhausted` как доказательство исчерпания. В срезе карты, продолжении к брифу и отчёте экспедиции рядом с `advisory_exhausted` SHALL указываться, что основание не является доказательством.

#### Scenario: Advisory помечен недоказанным
- **WHEN** направление в статусе `advisory_exhausted` показывается агенту (срез) или владельцу (отчёт)
- **THEN** рядом указано, что основание — самоотчёт по обзору, не доказательство

#### Scenario: Resolved с доказательством
- **WHEN** направление `resolved` показывается в срезе или отчёте
- **THEN** рядом указаны ссылки на закрывающие вердикты с доказательствами

### Requirement: Срез карты в продолжении

Единственное продолжение после промежуточного отчёта (правило «Режим исследования в цепочке») в экспедиционной цепочке SHALL включать срез карты: направления со статусами, их обоснования и последние решения. В не-экспедиционной цепочке продолжение остаётся без среза. Число продолжений и условие их отправки не меняются.

#### Scenario: Срез в экспедиции
- **WHEN** записан промежуточный отчёт кампании экспедиционной цепочки, статус `awaiting_child`
- **THEN** отправлено одно продолжение с бриф-указанием и срезом карты

#### Scenario: Обычная цепочка без среза
- **WHEN** записан промежуточный отчёт не-экспедиционной цепочки
- **THEN** продолжение отправляется как раньше, без среза карты

### Requirement: Стоп-предикат territory_complete

Предикат `territory_complete` SHALL быть чистой функцией карты: нет направлений в `open` или `active`; нет `pivot` после последнего закрывающего события; направлений когда-либо открыто не менее одного. В экспедиционной цепочке стоп-правило хартии с этим именем SHALL проверяться предикатом ДО любого изменения статуса цепочки: самоотчёт агента при `false` MUST отказывать с перечнем живых направлений (статус цепочки не меняется), при `true` — штатная остановка `stopped_by_rule`. Значение `true` означает только отсутствие открытых направлений, а не полноту исследования: пользовательские тексты формулируют результат как «предикат выполнен» с явным перечнем незакрытых направлений (parked, advisory) — формулировка «территория пройдена» как утверждение об успешном завершении не используется. Владелец (диалог `chain_stop`) может остановить экспедицию при любом значении предиката. В не-экспедиционной цепочке правило с этим именем ведёт себя по-старому (самоотчёт без проверки). Тайминговые эвристики (возраст, время с последнего события) MUST NOT участвовать в предикате.

#### Scenario: Самоотчёт при живых направлениях
- **WHEN** агент вызывает `chain_stop` с `rule_id: territory_complete`, а в карте есть `open` или `active`
- **THEN** отказ с перечнем открытых направлений; статус цепочки не меняется

#### Scenario: Предикат выполнен
- **WHEN** все направления закрыты или припаркованы и агент отмечает `territory_complete`
- **THEN** цепочка `stopped_by_rule`; в отчёте экспедиции зафиксировано «предикат выполнен» и перечень незакрытых направлений (parked, advisory)

#### Scenario: Pivot после последнего закрытия блокирует предикат
- **WHEN** после последнего закрывающего события карты записан `pivot`, и агент отмечает `territory_complete`
- **THEN** предикат `false`: отказ с указанием направления, открытого pivot'ом; статус цепочки не меняется

#### Scenario: Парковка не мешает
- **WHEN** единственное незакрытое направление `parked`
- **THEN** предикат `true`; парковка попадает в раздел незавершённого отчёта

#### Scenario: Не-экспедиционная цепочка
- **WHEN** в обычной charter-цепочке агент отмечает правило с именем `territory_complete`
- **THEN** остановка по-старому: самоотчёт без вычисления предиката

### Requirement: Виджет карты

При активной экспедиционной цепочке и `ctx.hasUI = true` виджет `autoresearch` SHALL рендерить карту: заголовок (цель, текущая кампания или статус цепочки), по строке на направление (глиф статуса, имя, активная кампания с открытыми вопросами или обоснование закрытия/парковки), футер (закрыто/всего направлений, кампаний/лимит, следующий шаг цепочки). Направление в статусе `advisory_exhausted` SHALL показываться в виджете с пометкой недоказанности основания. Виджет SHALL быть функцией от файлов (replay журнала). Вне экспедиции виджет остаётся обычным дашбордом без изменений. При `ctx.hasUI = false` виджет не рендерится и ошибок не возникает.

#### Scenario: Рендер карты
- **WHEN** экспедиционная цепочка активна, TUI доступен
- **THEN** виджет показывает карту: строки направлений с статусами, активную кампанию с открытыми вопросами, счётчики; advisory — с пометкой недоказанности

#### Scenario: Обычный дашборд не изменён
- **WHEN** режим исследования включён вне экспедиции
- **THEN** виджет рендерит обычный дашборд (регресс не допускается)

#### Scenario: Headless без ошибок
- **WHEN** экспедиция едет в сессии без UI
- **THEN** виджет не рендерится; ошибок и уведомлений об этом нет

### Requirement: Отчёт экспедиции

При любом финальном статусе экспедиционной цепочки система SHALL машинно собрать `expedition-report.md` в каталоге цепочки и включить его в ответ финального отчёта: карта (финальные статусы, основания, доказательства), хронология решений (открытия, активации, pivot'ы с обоснованиями), раздел незавершённого (парковки; advisory с пометкой «не доказательство»; направление, чья кампания остановлена без результата), вычисленное значение `territory_complete`, ссылки на отчёты всех кампаний. Отчёт MUST NOT содержать утверждений о покрытии территории или успешном завершении при незакрытых направлениях. Отчёт экспедиции не заменяет отчёты кампаний и не архивирует их.

#### Scenario: Финал с незакрытым
- **WHEN** цепочка остановлена владельцем при `parked`-направлении
- **THEN** отчёт записан; parked указан в незавершённом с формулировкой «не исследовано»; значение предиката соответствует карте

#### Scenario: Расхождение активного направления
- **WHEN** направление `active`, но его кампания остановлена без результата (abandon)
- **THEN** расхождение указано в разделе незавершённого; статус направления не подчищается

#### Scenario: Отчёт без хвастовства
- **WHEN** среди направлений есть `advisory_exhausted` и `parked`
- **THEN** отчёт не содержит формулировок полного завершения; advisory помечен недоказанным

#### Scenario: Отчёты кампаний сохраняются
- **WHEN** отчёт экспедиции собран
- **THEN** отчёты кампаний остаются на месте без архивации
