# Дизайн: ветки-кандидаты, MVP

**Draft rev.5 — согласованное владельцем упрощение защит; ожидает финального независимого ревью.** Утверждение и разрешение реализации даны в диалоге, но оно не отменяет проверки документа перед реализацией. Эта редакция заменяет сложный аварийный протокол rev.4.

## 1. Контекст и границы

Обычный `log_experiment` выполняет Git keep/discard (`extensions/pi-autoresearch/index.ts:4630, 5019–5103, 5192–5215`). Кандидатный цикл должен быть отдельным: существующий discard не должен откатывать работу кандидата. `PARALLEL_TOOLS_ENABLED=false` (`index.ts:2227`); `abortPhaseGit` не применяет вычисленный target (`parallel/phases.ts:212–220`). Включение старых режимов не является реализацией кандидатов. Research-map passport содержит декларации, а не проверенные файлы (`research-observations.ts:187–200`); его можно использовать для отображения, но не как единственное доказательство сопоставимости.

Одна кандидатная кампания на репозиторий, несколько кандидатов, не более одного активного. Только локальный Git и доверенные пользовательские команды; непараллельная работа нескольких Pi-сессий и отключённых инструментов. Защита при потере питания, повреждении ФС, посторонних Git-командах, небезопасном benchmark и других произвольных внешних процессах не обещается. Функция opt-in и не затрагивает обычные кампании вне режима.

## 2. Штатный цикл

1. Модель обсуждает с пользователем цель, метрику, направление, файлы, команды, число повторов, минимальный выигрыш и лимиты. Полные параметры показываются через UI; только явное подтверждение человека включает режим. Модель не может заменить подтверждение аргументом. Без UI — отказ.
2. Система фиксирует commit исходной базы и отдельный лидер кампании. Создание кандидата создаёт отдельный принадлежащий системе Git worktree от лидера и регистрирует кандидата; исходный worktree и чужие изменения не перемещаются и не изменяются.
3. Агент редактирует только worktree активного кандидата и запускает его измерения через кандидатный инструмент. Записанный локальный результат не становится глобальным keep.
4. Пользователь или агент сохраняет checkpoint: разрешённые изменения коммитятся в worktree кандидата, создавая отдельный идентификатор. Checkpoint становится выбранным; регрессия допустима. Чтобы переключить кандидата, несохранённые изменения должны быть сохранены; иначе переключение отказывает и ничего не удаляет.
5. Пользователь или агент приостанавливает кандидата и возобновляет другого. Checkpoint остаётся доступным. Закрытие кандидата не удаляет checkpoint.
6. По запросу подтверждения система повторно измеряет выбранный checkpoint и текущего лидера, проверяет контекст и checks. При достаточном улучшении автоматически переводит отдельный лидерский ref на проверенный commit; пользовательская ветка не переключается и не меняется. Иначе лидер прежний.

## 3. Политика и измерение

До init модель предлагает значения, пользователь подтверждает полный набор: `metric_name`, `direction` higher/lower, `repeats` ≥1, `min_gain` ≥0, `benchmark_argv`, `checks_argv`, timeout запуска и суммарный бюджет подтверждения, лимит шагов и времени кандидата, пути файлов методики и их SHA-256, выбранные файлы для изменений. Числа конечны, лимиты положительны; отсутствующее значение не подставляется молча. Политика неизменна внутри кампании; её изменение — новая кампания. Модель предлагает параметры, а не перекладывает весь выбор на пользователя.

Перед сравнением нужны доступные базовый и кандидатный commits, совпадающие метрика, направление, активная шкала/epoch и hash обязательных файлов методики, успешные выходы команд, конечные значения и успешные checks. Отсутствующая/неизвестная/изменённая обязательная зависимость, включая внешние данные, блокирует продвижение. Перечень зависимостей подтверждает человек; механизм не доказывает, что перечень полон, или что внешние сервисы детерминированы. Файлы методики не изменяются кандидатом. Доступность внешних весов по одному пути или hash не гарантируется.

В чистых отдельных worktree выполняются `repeats` измерений лидера и кандидата одинаковой командой. Направленный выигрыш = среднее кандидата минус среднее лидера для higher и наоборот для lower. Продвижение только при выигрыше строго больше `min_gain`, успешных checks для точного checkpoint и неизменной базе лидера. Ошибка, таймаут, неизвестный контекст, несопоставимость, равенство или неудачный checks — без продвижения. Repeats и порог — согласованное правило, не доказательство статистической значимости.

## 4. Минимальная защита

- До изменения Git проверять, что операция относится к созданному системой worktree и допустима в текущем состоянии; никогда не выполнять reset/clean/checkout или `git add -A` в исходном пользовательском worktree. Кандидатные коммиты включают только явно разрешённые файлы; наличие остальных несохранённых изменений блокирует сохранение/переключение с перечислением путей. Никакого автоматического удаления worktree в MVP.
- Сохранить состояние кампании и checkpoint refs на диске. Один простой эксклюзивный lock на кампанию используется всеми операциями режима, включая подтверждение; при занятом или сомнительном lock не начинать второй запуск. Lock после прерывания не снимать автоматически; оператор проверяет отсутствие работающего процесса. Обычные несовместимые инструменты расширения блокируются при включённом режиме; их штатное поведение вне режима не меняется.
- Перед созданием/переключением/продвижением фиксировать, что операция началась, и снимать отметку только после успешного завершения. При незавершённой операции, отсутствии данных, несоответствии ref или ошибке Git система сообщает состояние как требующее ручной проверки, не запускает следующие измерения и не удаляет данные. Оператор проверяет Git refs и имеющиеся worktree; автоматического восстановления или угадывания результата нет. Режим можно выключить только при отсутствии выполняющейся операции; файлы и refs при этом не удаляются.
- Лидер хранится в отдельном ref. Продвижение использует Git compare-and-swap с ожидаемым старым commit; при ошибке до переключения лидер прежний. При прерывании около переключения результат неопределён: статус явно сообщает это и требует ручной проверки, не заявляя ни старого, ни нового подтверждённого результата до проверки. Не обещается атомарная транзакция Git и файла состояния.
- Секреты в явно выбранных файлах автоматически не обнаруживаются; Git может сохранить их в истории. Символические ссылки и пути вне разрешённой области не включаются. Бинарные файлы допустимы только при явном выборе. Ограничения бюджета останавливают новые запуски без удаления checkpoint. Нет автоматического archive каждого обычного discard, автосборки мусора или хранения внешних весов.

## 5. Интерфейс и подсказки

Инструмент `candidate_branch` предоставляет действия `init`, `create`, `status`, `resume`, `run`, `checkpoint`, `pause`, `select`, `close`, `confirm`, `disable`. Идентификаторы кампании, кандидата и checkpoint возвращаются инструментом и используются в последующих вызовах. `status` показывает лидера, выбранный checkpoint, активного кандидата, бюджет, последнее измерение и ошибки/неопределённости. Запрещённые переходы не меняют файлы.

Встроенные системные промпты, resume/compaction/observer/council steers, tool descriptions, `skills/autoresearch-*` и шаблон `.auto/prompt.md` согласовать с выбранным режимом. В кандидатном режиме не предписывать обычный run/log или auto-revert; во внештатном состоянии предписывать остановку, а не автозапуск. Общая автономность не отменяет согласия человека на policy. Обычный режим сохраняет прежние инструкции. Существующий пользовательский `.auto/prompt.md` автоматически не перезаписывать. `autoresearch-parallel` не должен выдавать отключённые phases/SpaceSearch за работающие инструменты. См. `amendment-prompts-skills.md`.

## 6. Проверка и оценка

Тесты сосредоточены на сквозном штатном цикле, сохранении регрессивного checkpoint, переключении кандидатов и подтверждённом продвижении. Обязательные негативные проверки: грязный исходный worktree не меняется, второй активный кандидат отвергается, недоступный контекст/неудачные checks/устаревший лидер не продвигаются, прерванная операция не удаляет файлы и требует ручной проверки, обычный режим совместим с прежним. Проверки промптов охватывают оба режима и возобновление после сбоя. Для оценки пользы стратегии отдельно сравнить её с обычным циклом при сопоставимых бюджете измерений и времени, показывая разброс и затраты; реализация функции сама по себе не доказывает улучшения.

## 7. За рамками MVP

Транзакционный журнал intent/commit, registry ref, автолечение crash-состояний, гарантия полного учёта внешних данных, параллельные кандидаты, UCB, композиция веток, очистка checkpoint и полное файловое хранилище внешних артефактов. Риски и ограничения явно сообщаются пользователю в документации. Проверка атомарности на всех сочетаниях ФС и аварий питания не входит в MVP.
